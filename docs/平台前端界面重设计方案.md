# 私有化部署平台前端界面重设计方案

版本：V0.5 设计稿  
日期：2026-07-12  
依据：[私有化微服务部署平台产品需求文档](./私有化微服务部署平台产品需求文档.md)、[阶段3验收记录](./阶段3验收记录.md)

## 1. 设计结论

前端从“六个平行的管理页”调整为“以项目和服务为上下文的交付工作台”。用户的主路径固定为：

```text
项目 → 环境 → 应用 → 服务 → 制品 → 校验 → 发布 → 发布记录 / 回滚
```

界面只呈现 V0.5 已交付能力：已有镜像、Java 8 Jar、前端 dist、Docker tar、OCI archive、S3 Compatible 来源、受控包装/导入、已有 registry 推送、Docker 单机发布、配置、审计、回滚和原始制品清理。网关、域名证书、多主机、分批发布、Kubernetes、Git、源码构建、用户 Dockerfile/脚本和内置 registry 均不出现为可操作入口。

## 2. 当前界面审计

现有实现已有项目、应用、部署、制品、配置、发布六个 React 页面，并已接入项目权限、Endpoint 权限交集、制品状态、最终 tag/digest、配置预览和发布确认。重设计解决的是信息组织与操作密度，而不是绕过或重写这些服务端边界。

主要问题：

1. 平台页面集中在单个 `PlatformViews.tsx`，项目、应用、服务、运行态和操作表单分散在平行页面中，用户需要反复选择项目/应用/服务。
2. 制品列表虽已可上传、构建、推送、清理，但没有突出“当前状态、阻塞原因、下一步动作”，难以形成交付流水线心智。
3. 部署向导已具备最终制品选择与右侧摘要，但步骤仍以底层配置为中心，不能先回答“发布哪个服务、为什么可发布、失败时会怎样”。
4. 发布、配置、审计与运行态没有围绕同一服务展开的固定详情上下文；长 tag、digest、SHA256 和失败 reason 也缺少统一的展示规则。
5. 应用交付导航中混入 GitOps 项，容易误导用户认为平台支持 Git/源码交付；GitOps 若保留，应回归独立高级能力，不属于制品驱动主流程。

## 3. 信息架构

### 3.1 V0.5 主导航

| 区域 | 菜单 | 用户任务 | V0.5 说明 |
| --- | --- | --- | --- |
| 交付工作台 | 概览 | 看异常、待发布、待处理配置与最近发布 | 新增入口，非营销看板 |
| 交付工作台 | 项目与应用 | 选择项目，查看应用和服务运行状态 | 项目、环境、应用、服务的主要入口 |
| 交付工作台 | 发布服务 | 选择最终制品、校验并创建 Release | 复用现有发布 API |
| 交付工作台 | 制品库 | 上传/拉取、受控包装、导入、推送、清理 | 只显示受支持类型 |
| 交付工作台 | 发布记录 | 查看执行、失败、恢复、回滚 | 以服务和环境筛选 |
| 交付工作台 | 配置中心 | 项目/环境/服务三级配置及漂移 | 敏感值默认脱敏 |
| 高级管理 | Docker、镜像、网络等 | 保留 Portainer 原生运维入口 | 与应用交付分组，不进入主流程 |

GitOps Workflows 与 GitOps Sources 不再置于“应用交付”分组；若产品仍需保留这些上游能力，应放在独立的高级管理分组，并标注“不属于制品驱动交付流程”。

### 3.2 上下文栏

除“概览”外，所有主页面顶部使用一致的上下文栏：

```text
项目 [商城系统 ▾] / 环境 [生产 ▾] / 应用 [订单中心 ▾] / 服务 [订单 API ▾]
角色：项目管理员     Endpoint：docker-prod-01     服务状态：运行中
```

- 选择器按从左到右的归属关系级联；切换上级时清空下级选择。
- 无权限、没有 Endpoint 权限、缺少部署配置或不存在 `ready` 制品时，保留当前上下文并展示原因，不自动跳转或用空白页面掩盖问题。
- URL 应逐步承载选中 ID（例如 `?projectId=&environmentId=&applicationId=&serviceId=`），使刷新、分享和返回列表保持上下文。

## 4. 页面设计

### 4.1 交付概览

首页是操作看板，不使用大幅欢迎语或装饰图。首屏由四个紧凑指标、一个待处理队列和两个表格组成：

```text
┌ 项目 12 ┬ 运行服务 36 ┬ 异常服务 2 ┬ 待重新部署 4 ┐
├ 待处理 ───────────────────────┬ 最近失败发布 ───────────────────┤
│ • 订单 API：生产配置已变更      │ #281 订单 API  健康检查失败       │
│ • 管理后台：候选镜像待推送      │ #279 支付 API  已恢复旧版本       │
├ 最近发布 ──────────────────────┴────────────────────────────────┤
│ 时间 / 环境 / 服务 / 版本 / 状态 / 耗时 / 操作者 / 查看详情       │
└─────────────────────────────────────────────────────────────────┘
```

- 指标卡可点击进入已筛选的服务、发布或配置列表。
- “待处理”只展示真实状态：配置漂移、失败需人工处置、`built` 待推送、`ready` 待发布、可清理制品；不根据客户端猜测生成提示。
- 观察者可浏览状态与发布；操作按钮依服务端 Permissions 摘要置灰并显示授权原因。

### 4.2 项目与应用工作台

以项目为页面容器，环境是可切换的视角，应用与服务是同一张操作表：

```text
项目：商城系统  [开发] [测试] [生产]        + 创建应用   + 创建服务
─────────────────────────────────────────────────────────────────
订单中心                                      环境：生产
服务              当前版本      健康       配置       最近发布      操作
订单 API          2026.07.12    已验证     有漂移     #281 失败     查看
支付 API          2026.07.10    运行中     一致       #278 成功     查看
管理后台          2.4.0         运行中     一致       #280 成功     查看
─────────────────────────────────────────────────────────────────
最近发布 / 项目配置 / 成员与权限（标签页）
```

- 环境标签明确显示生产标识；生产环境顶部固定显示“单机 replace 可能短暂停机”的安全提示。
- 应用行可折叠或进入应用详情；服务行进入服务工作台，不再要求用户在独立页面重新选择同一服务。
- 项目管理员才能看到成员管理与原始制品清理入口；开发者可见部署入口；观察者只读。

### 4.3 服务工作台

服务详情使用“固定运行摘要 + 标签页”，将发布前后的事实放在同一上下文。

| 标签 | 内容 | 主要动作 |
| --- | --- | --- |
| 概览 | 当前版本、最终 image/digest、运行状态、Endpoint、端口、健康结果、最后发布、配置漂移 | 查看日志、发布新版本、重新部署、回滚 |
| 配置 | 有效配置、来源层级、revision、漂移状态、敏感字段名 | 查看差异、编辑、重新部署 |
| 制品 | 关联制品、SHA256、来源、受控模板、tag/digest、保留与可清理状态 | 上传/拉取、包装/导入、推送、清理 |
| 发布 | Release 时间线、执行步骤、失败 reason、恢复/回滚关系 | 查看详情、确认回滚、人工处置 |
| 日志 | 运行日志、关键词、最近行数 | 复制受限日志、刷新 |
| 审计 | 当前项目/应用/服务的结构化审计 | 按动作/结果筛选 |

运行摘要固定使用状态芯片：`运行中`、`异常`、`未部署`、`配置已变更`、`待人工处置`。所有 image tag、digest 和 SHA256 使用等宽字体、截断显示与“复制摘要”按钮；复制前只复制公开的 tag/hash，不复制敏感配置或实际存储路径。

### 4.4 制品库

制品库以“状态驱动表格 + 右侧详情抽屉”替代多个散落的操作表单。表格建议列：

| 名称 | 类型/来源 | 关联服务 | 原始 SHA256 | 当前状态 | 最终镜像 | 保留 | 下一步 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| order-api.jar | Java 8 Jar / 上传 | 订单 API | `1a2b…9c3e` | 已构建 | 候选镜像 | 已保留 | 推送到 registry |
| admin-dist.zip | dist / S3 Compatible | 管理后台 | `7b2f…da01` | 已就绪 | `registry/...:2.4.0` | 可清理 | 发布服务 |

- 顶部的“新增制品”只打开来源选择：已有镜像、手动上传、S3 Compatible。选择后进入类型受限的表单。
- 行内主操作由状态决定：`uploaded/fetched` → 校验/准备，`built` → 推送，`ready` → 发布，`failed` → 查看脱敏 reason/重试，`cleanable` → 清理确认。
- 详情抽屉分为“事实、处理记录、关联发布、保留策略”四组；从不显示凭据、签名 URL、服务器路径或制品内容。
- Jar 页面只提供 Java 8、端口、受限 JVM/App token；dist 页面只提供 SPA/MPA、缓存、可选 dist 内 404；archive 只展示已解析的元信息，不接收 Dockerfile 或 shell。

### 4.5 发布服务向导

V0.5 保留八阶段的语义，但将界面合并为六个可理解的步骤，避免显示未实现的网关能力：

1. **目标服务**：项目、环境、应用、服务；显示角色和 Endpoint 权限。
2. **选择可发布制品**：优先列出匹配服务类型的 `ready` Artifact；可退回到已有 image reference。展示原始 SHA256、最终 tag/digest、来源和强/弱追溯。
3. **运行与健康检查**：端口、HTTP/TCP、验证级别；生产环境只允许已验证健康检查。
4. **配置预览**：展示项目 > 环境 > 服务的有效配置、漂移、敏感字段数量；不显示敏感值。
5. **发布前校验**：按检查项展示通过、阻断、警告；阻断项直接定位回步骤，警告说明风险和后果。
6. **确认并发布**：显示执行计划、当前线上版本、失败恢复承诺、不可变快照与生产二次确认。

右侧固定摘要贯穿全部步骤：目标服务、制品、最终镜像、版本、Endpoint、健康检查、配置修订、校验状态。没有 `ready` 制品时，摘要明确显示“请先在制品库完成推送”，并提供导航链接而不是允许误发起发布。

### 4.6 发布记录与回滚

发布记录默认按当前项目和环境筛选，表格列固定为：Release、服务、版本、状态、触发方式、最终镜像/digest、操作者、开始时间、耗时、回滚可用性、失败 reason。点击行打开详情抽屉：

```text
发布 #281 / 订单 API / 生产
执行：校验 ✓ → 部署 ✓ → 健康检查 ✕ → 恢复旧版本 ✓
失败原因：HEALTH_CHECK_FAILED（脱敏）
当前线上版本：2026.07.10
快照：Artifact / Config / Secret（只显示摘要）
[查看日志] [查看配置差异] [回滚到此版本]
```

回滚必须先展示 image、端口、配置字段名和敏感变量“是否有值”的差异；生产环境使用二次确认。若 release 不可回滚，展示具体事实，例如镜像不可用或当前服务存在任务锁。

### 4.7 配置中心

配置采用左侧作用域树、右侧有效值和底部变更影响区：

```text
项目：商城系统
├ 项目级
├ 生产
│  └ 订单 API / #17
└ 测试

KEY              有效值/状态        来源          影响
LOG_LEVEL        info                环境级        一致
PAYMENT_TOKEN    已设置（敏感）      服务级        需重新部署
```

- 清晰区分继承、覆盖、敏感、缺失和已归档配置。
- 敏感变量默认展示“已设置/未设置”，查看或复制要有权限、二次确认和审计。
- 服务运行且配置有变化时，顶部展示“配置已变更，当前运行实例尚未重新部署”，提供“查看差异”和“发布服务”。

## 5. 状态、权限与安全视觉规范

### 5.1 状态颜色

| 语义 | 颜色 | 示例 |
| --- | --- | --- |
| 成功/运行/已验证 | 绿色 | `ready`、发布成功、健康检查通过 |
| 处理中 | 蓝色 | 校验、构建、导入、推送、部署中 |
| 需关注 | 琥珀色 | 配置漂移、弱追溯、原始制品待保留、生产短暂停机风险 |
| 失败/人工处置 | 红色 | 构建失败、健康检查失败、恢复失败 |
| 只读/已归档 | 灰色 | viewer、归档资源、已清理原始副本 |

状态必须同时有文本和图标，不只依赖颜色。失败 reason 采用受控 reason code 加中文解释，不回显底层错误原文。

### 5.2 权限反馈

- 无操作权限：按钮置灰，悬浮/行内解释“需要项目管理员”或“需要目标 Endpoint 访问权限”。
- 无敏感权限：字段仍可见为掩码，查看/复制控件不可用，并说明不会显示明文。
- API 失败：使用统一错误条显示脱敏 reason；页面权限判断仅优化体验，绝不把前端隐藏视为授权。

### 5.3 主题与长文本

- 所有面板使用现有浅色、深色、高对比主题类；不得依赖固定白底或纯色背景。
- 1280px 以上使用“表格 + 详情抽屉 / 右侧摘要”；窄屏转为卡片列表和抽屉，操作收进更多菜单。
- 名称最多两行；tag/digest/SHA256 可换行并可复制摘要；路径仅展示逻辑对象键，真实宿主机路径不可进入 UI。

## 6. 实施拆分

| 优先级 | 切片 | 前端改造 | 后端依赖 |
| --- | --- | --- | --- |
| P0 | 导航与共享上下文 | 新增交付概览路由、统一 ContextBar、移出交付分组中的 GitOps 项、统一状态芯片/空状态/权限提示 | 复用现有查询；概览可先由既有项目、制品、发布聚合 |
| P0 | 项目与服务工作台 | 项目/应用页合并为环境视图与服务表；服务详情标签页 | 复用现有部署状态、日志、配置、审计、Release API |
| P0 | 制品状态驱动界面 | 制品表格、详情抽屉、按状态的下一步操作、统一确认面板 | 复用上传、构建、导入、推送、清理 API |
| P0 | 发布向导重排 | 将现有字段重组为六步、增加阻断校验清单与上下文摘要 | 复用 validate/create Release API，不改变事务或锁 |
| P1 | 发布记录详情 | 筛选器、执行步骤时间线、回滚差异抽屉 | 复用 Release、rollback diff、resolve API |
| P1 | 配置中心双栏 | 作用域树、有效配置和漂移影响区 | 复用 config set/effective config API |
| P2 | V1.0 占位能力 | 域名、网关、多主机仅在功能实际交付后增加 | 未实现前不创建可操作入口 |

建议将现有超大的 `PlatformViews.tsx` 拆分为 `views/`、`components/`、`deploy/`、`artifacts/`、`service/` 与 `shared/`；每个切片独立补齐中英文 i18n、响应式和权限态测试。此拆分只重组前端，不改变 `/api/platform` 契约。

## 7. 验收清单

1. 管理员、项目管理员、开发者、观察者在同一服务上下文看到正确的可用操作；直接 API 仍由后端拒绝越权请求。
2. 用户能在不重复选择项目/应用/服务的情况下完成“ready 制品 → 校验 → 发布 → Release 详情 → 回滚”的主路径。
3. Jar、dist、Docker tar、OCI archive 和 S3 Compatible 制品都可从制品状态看到下一步、最终 tag/digest、SHA256、保留和清理限制。
4. 页面不展示 Git、源码构建、Dockerfile、shell、内置 registry、网关/多主机等 V0.5 不支持动作。
5. 中文、英文、浅色、深色和高对比主题下，长文件名、tag、digest、SHA256、失败 reason 与权限提示均可阅读。
6. 敏感变量、registry/对象存储凭据、签名 URL、原始制品内容和服务器真实路径不进入表格、抽屉、toast、审计或测试快照。

## 8. 本轮落地（P0）

- 新增“交付概览”路由和导航入口：基于既有项目、制品和发布查询展示活跃项目、已就绪制品、发布数量、需关注发布、待推送候选镜像、可发布制品和可清理原始副本；统计只读取服务端事实。
- 应用交付侧栏调整为“交付工作台”，移除其中的 GitOps 入口，避免把 Git/源码交付误解为 V0.5 能力；GitOps 路由没有删除。
- 制品页新增交付流程说明、状态统计和“下一步”列，明确 `built` 推送、`ready` 发布、失败复查、Jar/dist 受控包装和原始副本清理的行动方向。
- 发布向导从八个分散步骤收敛为六步：目标服务、选择制品、运行与健康检查、配置与执行计划、发布前校验、确认。最终 tag/digest、配置预览和服务端校验/创建 Release API 保持不变。
