## 3. 阶段 4 冻结契约

### 3.1 单机范围

1. 阶段 4 仅支持一个已启用 gateway target 和一个已启用 workload target 的单机环境。多 workload target、主机组、分批发布与跨主机 upstream 留给阶段 5。
2. HTTP 服务的 upstream 必须指向平台在本次 Release 中记录的 published host port；阶段 4 不访问容器内部 IP，不接受用户输入的 upstream 地址或原始 Nginx 配置。
3. 非 HTTP 服务（worker、scheduler、python-job 等）不得创建网关路由。

### 3.2 路由与证书

1. 路由归属固定为 Project、PlatformEnvironment 和 ServiceDeployment；记录规范化域名、以 `/` 开始的路径、服务目标端口、HTTPS/强制 HTTPS、WebSocket、代理超时、最大上传大小及可选证书引用。
2. 域名不支持通配符；同一环境中规范化后的相同 `domain + path` 必须唯一。根路径 `/` 与子路径的排序由渲染器确定，不能依赖写入顺序。
3. 手动证书必须校验 PEM、证书和私钥匹配、有效期，并将私钥放入受控存储。API 只返回元数据和是否存在私钥，不返回私钥、证书原文或受控文件路径。

### 3.3 安全配置发布

1. 路由、证书与 Release 均保存不可变安全摘要；Release 的 `GatewaySnapshot` 至少包含域名、路径、upstream、配置 hash、前后配置版本和证书引用。
2. 渲染器只能使用模型的枚举/数值/严格校验字段，拒绝换行、控制字符和 Nginx 指令注入。
3. 配置发布顺序固定为：读取活动版本 → 写入隔离候选版本 → `nginx -t` → 原子激活候选版本 → reload → 持久化成功快照。任何一步失败都不得把候选配置声明为活动版本。
4. reload 失败时必须恢复前一配置并再次 reload；恢复失败要写固定 failure reason、保留人工处置事实并禁止把 Release 记为成功。

### 3.4 发布补偿

1. 新 Release 在 candidate 健康检查通过后才允许尝试网关切流；网关预检/test/reload 失败时，当前线上路由和 `CurrentServingReleaseID` 保持不变。
2. 人工回滚和重试恢复使用历史 Release 的 GatewaySnapshot，不根据当前路由表重建旧流量。
3. 网关 Docker/Agent 操作、文件写入、`nginx -t`、reload 和网络验证都在 datastore 事务外执行；事务仅保存版本、快照、状态和审计。
