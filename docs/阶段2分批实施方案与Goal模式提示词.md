## 1. 总体结论

阶段 1 已打通 V0.1 Docker 单机已有镜像发布闭环。阶段 2 的目标不是进入制品构建、对象存储、中心 Nginx 网关或多主机发布，而是补齐 V1.0 MVP 所需的基础安全能力：配置中心、敏感变量、配置快照和漂移、基础 RBAC、结构化审计、人工历史版本回滚。

阶段 2 拆成 8 批实现。每批必须先审计现状和文档边界，再实现、验证、提交，并更新阶段 2 进度记录后进入下一批。

阶段 2 明确不做：

- 不做 Jar / dist / image tar / OCI archive 制品构建或导入；这些属于阶段 3。
- 不做 MinIO / S3 对象存储拉取制品；这些属于阶段 3。
- 不做标准 tag 推送已有 registry；这些属于阶段 3。
- 不做中心 Nginx 网关、域名、证书和网关切流；这些属于阶段 4。
- 不做多 Docker 主机、跨主机分批发布；这些属于阶段 5。
- 不做 Kubernetes、Git、源码构建、内置 registry、完整 CI/CD、审批流。

## 3. 分批实施方案

### 3.1 批次 1：阶段 2 基线审计与方案冻结

目标：在正式编码前，把阶段 2 的安全边界、接口草案、数据模型缺口和验收用例固化到 docs，避免把阶段 3/4/5 能力提前纳入。

范围：

- 新增或维护 `docs/阶段2实施进度.md`。
- 审计阶段 1 当前实现：模型、发布快照、审计、前端页面、权限限制、Docker 执行器。
- 从 PRD、阶段 0 设计稿和排期中提取阶段 2 权威范围。
- 补充阶段 2 API 草案：配置中心、敏感变量、RBAC、审计查询、人工回滚。
- 列出阶段 2 验收用例和风险项。

不做：

- 不改业务代码。
- 不放开非管理员权限。
- 不实现配置中心或回滚 API。

交付物：

- `docs/阶段2实施进度.md`
- 必要的设计或 API 文档补充

验收标准：

- 文档明确阶段 2 只覆盖配置、安全、权限、审计、人工回滚。
- 文档明确阶段 3/4/5 红线。
- 进度文档包含批次、验证命令、提交哈希、遗留风险字段。

建议提交信息：`docs: 固化阶段2实施方案`

### 3.2 批次 2：配置中心模型与 dataservice

目标：建立三级配置中心的持久化基础，让项目级、环境级、服务部署级配置可版本化保存。

范围：

- 新增或补齐 `PlatformConfigSet`、`PlatformConfigEntry`、`PlatformSecretRef`、`EffectiveConfigSnapshot`、`PlatformConfigEntrySnapshot`、`SecretSnapshot` 等模型。
- 实现 ConfigSet dataservice、BoltDB bucket、事务读写、Export/Import。
- 支持 `ScopeType=project/environment/service-deployment`、`ScopeID`、`Name=default`、`Revision`。
- 支持普通配置和敏感配置元数据，但本批不开放敏感值明文 reveal。
- 增加默认值、revision 递增、逻辑归档或删除策略。

不做：

- 不做前端页面。
- 不做发布注入敏感值。
- 不做 RBAC 放开。

交付物：

- 配置中心模型和 dataservice。
- 迁移、Export/Import 和单元测试。

验收标准：

- ConfigSet 可按作用域创建、读取、更新、归档。
- Revision 在配置内容变更时递增。
- 普通值和敏感值元数据不会破坏阶段 1 发布链路。

建议验证：

```powershell
go test ./api/platform ./api/dataservices/... -count=1
```

建议提交信息：`feat: 新增平台配置中心模型`

### 3.3 批次 3：配置中心 API 与配置合并

目标：提供配置中心 CRUD API，并实现项目级 < 环境级 < 服务部署级覆盖合并和配置漂移判断。

范围：

- 新增 `/api/platform/config-sets` 或等价资源 API。
- 支持按项目、环境、服务部署查询配置集。
- 支持创建、更新、归档配置项。
- 实现有效配置计算 API：合并项目级、环境级、服务部署级 `EnvOverrides`。
- 将 `ConfigSetRevisions`、`Entries` 和 `ConfigHash` 写入发布前快照构造逻辑。
- 当配置 revision 与当前成功发布快照不一致时，标记或返回 `config-changed` 漂移。

不做：

- 不解密或展示敏感变量明文。
- 不实现人工回滚。
- 不开放非管理员。

交付物：

- 配置中心 handler / service。
- 有效配置合并逻辑。
- 配置漂移接口或状态更新。

验收标准：

- 三级配置合并顺序正确，后层覆盖前层。
- 删除或修改上层配置后，有效配置和 hash 可预测。
- 当前运行版本可以显示配置漂移状态。

建议验证：

```powershell
go test ./api/http/handler/platform ./api/platform -count=1
```

建议提交信息：`feat: 新增平台配置中心 API`

### 3.4 批次 4：敏感变量加密、脱敏与注入

目标：让敏感变量具备可保存、可脱敏展示、可权限控制 reveal、可发布注入和可回滚快照的最小闭环。

范围：

- 复用或增强 Portainer 现有加密能力保存敏感值。
- API 响应默认只返回变量名、是否敏感、是否有值、hash 或版本信息，不返回明文或密文。
- reveal/copy 敏感值必须经过独立权限检查并写审计。
- 发布时合并普通配置和敏感变量，注入到 Docker 容器环境变量。
- Release 快照保存 `SecretSnapshots`：变量名、密钥版本、密文或可回滚引用、密文 hash，不保存明文。
- 日志、错误、审计、前端 toast 均不得包含敏感明文。

不做：

- 不做外部密钥管理系统。
- 不做复杂密钥轮换 UI。
- 不做配置审批。

交付物：

- 敏感变量保存和脱敏 API。
- 发布注入和 Release SecretSnapshots。
- 敏感字段审计和测试。

验收标准：

- 敏感明文不落 BoltDB 非加密字段。
- 非授权用户不能 reveal/copy。
- 发布后的容器能收到敏感环境变量，但 API、日志、审计不泄漏明文。
- 删除原配置后，回滚仍能使用 Release 快照中的敏感配置；密钥不可用时回滚校验失败。

建议验证：

```powershell
go test ./api/http/handler/platform ./api/platform -count=1
rg -n -i "password|secret|token|Authorization|Registry@123456|minio123" api docs
```

建议提交信息：`feat: 支持平台敏感变量加密注入`

### 3.5 批次 5：基础 RBAC 与 Endpoint 权限交集

目标：从“管理员全量访问”升级为 V1.0 基础项目角色权限，同时保留全局管理员最高权限和 Endpoint 权限交集约束。

范围：

- 实现项目成员、团队策略和角色字段的读写或启用阶段 1 已预留字段。
- 支持角色：全局管理员、项目管理员、开发者、只读观察者。
- 平台项目权限与 Portainer Endpoint 权限取交集。
- 无对象访问权的读请求返回 404；明确操作已知对象但权限不足返回 403。
- 按阶段 0 权限矩阵覆盖配置、发布、日志、敏感变量、审计、回滚权限。
- 前端根据权限隐藏或禁用不可用操作，并保留直接访问 API 的后端保护。

不做：

- 不做复杂审批流。
- 不做租户隔离或计费。
- 不做网关/证书权限。

交付物：

- 平台 RBAC 判定服务。
- Handler 权限改造。
- 前端权限态处理。
- 权限矩阵测试。

验收标准：

- 管理员能力不回退。
- 项目管理员可管理项目内环境、应用、服务、配置、发布和回滚。
- 开发者可按授权上传或登记制品、发起发布、看日志状态；不能管理敏感变量明文和项目成员。
- 只读观察者只能查看项目、服务、发布、日志和状态。
- 无 Endpoint 权限时不能部署、看日志或读运行态。

建议验证：

```powershell
go test ./api/http/handler/platform ./api/platform -count=1
pnpm typecheck
```

建议提交信息：`feat: 新增平台基础 RBAC`

### 3.6 批次 6：结构化平台审计扩展

目标：把阶段 1 的最小发布审计扩展为 V1.0 基础结构化审计，覆盖配置、安全、权限和回滚关键操作。

范围：

- 扩展 `PlatformAuditLog` action 枚举和写入点。
- 覆盖配置创建、更新、归档。
- 覆盖敏感变量创建、修改、reveal/copy、删除。
- 覆盖权限变更、成员变更、denied 事件。
- 覆盖人工历史回滚创建、成功、失败。
- 补齐 `BeforeSummary`、`AfterSummary`、`FailureReason`、`SensitiveFields`。
- 新增审计查询 API：按项目、环境、应用、服务、发布、操作者、action、result、时间范围筛选。
- 前端新增审计日志页面骨架或项目内审计视图。

不做：

- 不保存敏感明文。
- 不保存 Nginx 完整运行配置。
- 不做审计导出或长期归档策略。

交付物：

- 审计写入扩展。
- 审计查询 API。
- 审计页面骨架。
- 审计测试。

验收标准：

- 关键安全操作都有结构化审计。
- denied 事件可追踪对象和原因。
- 审计摘要不含敏感明文。
- 前端可按项目或操作类型查看审计记录。

建议验证：

```powershell
go test ./api/http/handler/platform ./api/platform -count=1
pnpm typecheck
```

建议提交信息：`feat: 扩展平台结构化审计`

### 3.7 批次 7：人工历史版本回滚

目标：开放从历史成功 Release 中选择版本并创建回滚 Release 的能力，区别于阶段 1 的失败自动恢复旧容器。

范围：

- 新增 `POST /api/platform/releases/{releaseId}/rollback` 或等价 API。
- 回滚前校验历史 Release 状态、镜像/digest 可用性、目标环境、服务部署、配置快照、敏感快照和当前锁状态。
- 回滚 Release 记录 `RollbackSourceReleaseID`。
- 展示当前版本与目标历史版本的镜像、配置、端口、环境变量、敏感变量摘要 diff。
- 回滚执行复用阶段 1 Docker 单机发布执行链路。
- 回滚失败不得破坏当前线上版本；失败 reason 和审计必须明确。
- 生产环境回滚需要二次确认。

不做：

- 不做批量回滚。
- 不做网关切流回滚。
- 不做跨主机回滚。

交付物：

- 回滚 API 和状态机接入。
- 回滚校验和 diff。
- 前端发布记录中的回滚入口。
- 回滚审计。

验收标准：

- 可选择历史成功 Release 回滚。
- 回滚创建的是新的 Release 事实，不改写历史 Release。
- 回滚失败保留当前运行版本。
- 敏感快照缺失或密钥不可用时回滚校验失败。

建议验证：

```powershell
go test ./api/http/handler/platform ./api/platform -count=1
pnpm typecheck
```

手工验收：

- 发布 v1 成功。
- 发布 v2 成功。
- 从发布记录选择 v1 回滚。
- 回滚成功后服务访问到 v1。
- 模拟镜像缺失或端口冲突时回滚失败且 v2 保持可用。

建议提交信息：`feat: 支持平台历史版本回滚`

### 3.8 批次 8：前端整合与阶段 2 验收

目标：把配置中心、敏感变量、RBAC、审计和人工回滚整合成可用的阶段 2 用户路径，并形成验收记录。

范围：

- 前端新增或完善配置中心页面：项目级、环境级、服务部署级配置。
- 部署向导支持选择或预览有效配置，显示配置漂移。
- 敏感变量默认脱敏，reveal/copy 需权限和确认。
- 发布记录展示配置快照摘要、敏感变量摘要和回滚入口。
- 审计日志页面支持筛选和详情查看。
- 权限不足时 UI 隐藏或禁用操作，直接访问显示清晰错误态。
- 新增阶段 2 手工验收记录。

不做：

- 不做大屏、营销页或仪表盘装饰。
- 不做实时日志 WebSocket 以外的新增实时系统。
- 不做阶段 3/4/5 能力入口。

交付物：

- 阶段 2 前端页面和 i18n。
- 阶段 2 验收记录。
- 必要的 API 文档更新。

验收标准：

- 管理员可以完成配置创建、敏感变量保存、发布注入、审计查看和历史回滚。
- 项目管理员、开发者、只读观察者权限表现符合矩阵。
- 中英文文案齐全。
- 深色/浅色主题下表单、表格、diff、审计详情不重叠。
- 阶段 2 测试和手工验收通过。

建议验证：

```powershell
pnpm typecheck
go test ./api/http/handler/platform ./api/platform -count=1
```

建议提交信息：`feat: 完成阶段2前端整合验收`

## 4. Goal 模式总控提示词

```text
目标：根据 docs/阶段2分批实施方案与Goal模式提示词.md，按批次 1 到批次 8 顺序完成阶段 2 开发。每一批必须实现、测试通过、提交对应代码并更新 docs/阶段2实施进度.md 后，才能进入下一批。

工作方式：

1. 先读取并遵守以下文档：
   - AGENTS.md
   - docs/阶段2分批实施方案与Goal模式提示词.md
   - docs/阶段1实施进度.md
   - docs/阶段0平台核心模型与后端边界设计.md
   - docs/私有化微服务部署平台产品需求文档.md

2. 先审计当前状态：
   - 执行 git status --short --branch。
   - 执行 git log --oneline -n 30。
   - 搜索阶段 2 相关代码和文档：ConfigSet、ConfigEntry、SecretRefs、EffectiveConfigSnapshot、PlatformAuditLog、RollbackSourceReleaseID、RBAC。
   - 判断当前应从哪个批次继续。不要重复已经有提交和测试证据证明完成的批次；证据不足时先补验证或补缺口。

3. 按批次顺序推进：
   - 批次 1：阶段 2 基线审计与方案冻结。
   - 批次 2：配置中心模型与 dataservice。
   - 批次 3：配置中心 API 与配置合并。
   - 批次 4：敏感变量加密、脱敏与注入。
   - 批次 5：基础 RBAC 与 Endpoint 权限交集。
   - 批次 6：结构化平台审计扩展。
   - 批次 7：人工历史版本回滚。
   - 批次 8：前端整合与阶段 2 验收。

4. 每批开始前必须做批次审计：
   - 从 docs/阶段2分批实施方案与Goal模式提示词.md 提取本批目标、范围、不做项、依赖、交付物、验收标准。
   - 搜索当前代码和文档，确认本批缺口。
   - 制定本批实现计划并用 update_plan 跟踪。

5. 阶段 2 红线：
   - 不实现 Jar/dist/image tar/OCI archive 制品构建或导入。
   - 不实现 MinIO/S3 对象存储拉取制品。
   - 不实现标准 tag 推送已有 registry。
   - 不实现中心 Nginx 网关、域名、证书、网关切流。
   - 不实现多 Docker 主机、跨主机分批发布。
   - 不实现 Kubernetes、Git、源码构建、内置 registry、完整 CI/CD、审批流。
   - 不把敏感变量明文写入 BoltDB 非加密字段、日志、审计、错误消息、前端 toast 或测试快照。
   - 不回滚用户或其他协作者已有改动；只提交本批相关文件。

6. 每批实现规则：
   - 优先沿用仓库已有 Portainer handler、dataservice、service、React、i18n、错误处理和测试风格。
   - 后端权限必须有服务端强制校验，前端隐藏或禁用只能作为体验优化。
   - 项目权限必须与 Portainer Endpoint 权限取交集。
   - 人工历史回滚必须创建新的 Release 事实，不得改写历史 Release。
   - 回滚失败不得破坏当前线上版本。
   - 配置合并顺序必须是：项目级 < 环境级 < 服务部署级 EnvOverrides。
   - 审计摘要必须脱敏，SensitiveFields 只记录字段名。

7. 每批验证规则：
   - 后端模型、dataservice、handler、权限、审计或状态机改动后，运行相关 go test。
   - 前端 TypeScript 改动后，运行 pnpm typecheck。
   - 敏感变量相关批次必须额外搜索明文泄漏风险。
   - 如果测试失败，先修复并重跑；不得在测试失败时提交，除非失败明确与本批无关并在回复中给出证据。

8. 每批提交规则：
   - 每批完成并验证后，执行 git status --short，确认只包含本批相关改动。
   - stage 本批相关文件。
   - 使用中文 commit message，建议：
     - 批次 1：docs: 固化阶段2实施方案
     - 批次 2：feat: 新增平台配置中心模型
     - 批次 3：feat: 新增平台配置中心 API
     - 批次 4：feat: 支持平台敏感变量加密注入
     - 批次 5：feat: 新增平台基础 RBAC
     - 批次 6：feat: 扩展平台结构化审计
     - 批次 7：feat: 支持平台历史版本回滚
     - 批次 8：feat: 完成阶段2前端整合验收
   - 提交成功后，在回复中说明本批提交哈希、验证命令和结果，再继续下一批。

9. 进度记录：
   - 维护 docs/阶段2实施进度.md。
   - 每批提交后记录：批次、提交哈希、完成内容、验证命令、测试结果、遗留风险、是否允许进入下一批。

10. 完成判定：
   - 只有批次 1 到批次 8 都有提交、验证结果和当前状态证据证明完成后，才能把 Goal 标记为 complete。
   - 如果遇到缺少真实 Docker/Agent/权限用户/浏览器环境等外部条件，先完成可本地推进的验证和文档记录；只有同一阻塞条件连续三轮仍无法推进时，才按 Goal 模式 blocked 规则处理。

从现在开始执行：先审计当前仓库状态，判断应该从第几批继续，然后按上述规则推进。
```

## 5. Goal 模式续跑提示词

中断后继续阶段 2 Goal 时，复制下面提示词。

```text
继续当前阶段 2 Goal。

请先读取：
- docs/阶段2分批实施方案与Goal模式提示词.md
- docs/阶段2实施进度.md（如果存在）
- docs/阶段1实施进度.md
- git log --oneline -n 30
- git status --short --branch

然后判断下一步：
1. 如果上一批已经提交且测试证据充分，进入下一批。
2. 如果上一批有提交但测试证据不足，先补验证；必要时补修复提交。
3. 如果上一批未提交，继续完成该批，实现、测试、提交并更新 docs/阶段2实施进度.md 后再进入下一批。
4. 如果发现当前改动包含用户并行工作，先识别范围，只暂存和提交本批相关文件，不得回滚用户改动。

仍然必须遵守：
- 每批实现、测试通过、中文 commit 后再进入下一批。
- 不提交无关文件。
- 不实现阶段 3/4/5 能力。
- 不泄漏敏感变量明文。
- 后端权限必须服务端强制校验。
- 人工历史回滚必须创建新的 Release，不得改写历史 Release。
```

## 6. 批次完成审计清单

每一批提交前，Codex 必须逐项确认：

- 本批目标、范围、不做项、依赖、交付物、验收标准已从本文件对齐。
- 当前改动没有越过阶段 2 边界。
- 相关 Go 测试、前端类型检查或文档检查已运行。
- 敏感变量相关改动已经检查明文泄漏。
- RBAC 相关改动已经覆盖管理员、项目管理员、开发者、只读观察者和无 Endpoint 权限场景。
- 回滚相关改动已经覆盖成功回滚、回滚失败不破坏当前版本、敏感快照不可用失败。
- `git status --short` 只包含本批相关文件，或已明确排除用户并行改动。
- commit message 使用中文。
- `docs/阶段2实施进度.md` 已记录本批提交和验证结果。

## 7. 阶段 2 最小验收用例

阶段 2 完成时至少通过以下用例：

1. 管理员创建项目级、环境级、服务部署级配置，发布时按项目级 < 环境级 < 服务部署级顺序合并。
2. 修改配置后，服务详情或部署配置显示配置漂移。
3. 敏感变量保存后 API 默认脱敏，未授权用户不能 reveal/copy。
4. 发布容器能收到敏感环境变量，但日志、审计、错误消息不包含明文。
5. 项目管理员可以管理项目内配置和发布，不能管理全局项目。
6. 开发者在授权范围内可发起发布和看日志，不能查看敏感变量明文。
7. 只读观察者只能查看项目、服务、发布、日志和状态。
8. 无 Endpoint 权限的用户不能部署、看日志或读运行态。
9. 配置、敏感变量、权限变更、denied、发布和回滚均写入结构化审计。
10. 发布 v1、发布 v2 后，可选择 v1 创建回滚 Release，并回到 v1。
11. 回滚目标镜像缺失、敏感快照不可用或端口冲突时，回滚失败且当前版本保持可用。
12. 中英文 UI、深色/浅色主题、长镜像名、长变量名和审计详情不破坏布局。
