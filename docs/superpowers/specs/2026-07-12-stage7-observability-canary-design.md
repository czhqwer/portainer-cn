# 阶段 7 设计：受限可观测性与最小 HTTP 灰度

## 目标与范围

本设计只实现以下后端能力：

1. 接入客户既有 Prometheus、Loki、Grafana，提供受权限约束的观测查询。
2. 在既有中心 Nginx 网关上支持两个已验证 Release 的人工 HTTP 灰度放量。

不部署观测组件、不代理 Grafana Dashboard、不接受任意 PromQL/LogQL、不做自动放量、不实现 ACME 或 Kubernetes。

## 方案选择

### 可观测性

可选方案包括：

- 任意查询代理：灵活，但会绕过查询成本、租户隔离和敏感标签边界，拒绝采用。
- 固定模板：安全、可审计且符合当前平台模型，采用。
- 每项目自定义模板：需要额外 DSL、审核和成本控制，留给后续增强。

采用固定模板。模板标识、允许时间窗、最大序列数和最大日志行数在服务端固定；调用方只能传项目、环境、服务部署及有效时间范围。

### 灰度

可选方案包括：

- Nginx 动态权重模块：增加运行时依赖与故障面，拒绝采用。
- 受控配置重渲染：复用已有候选配置、预检、原子激活和 reload 恢复链路，采用。
- 按指标自动放量：依赖可靠的指标阈值与自动补偿策略，留给后续增强。

采用受控配置重渲染。灰度状态只允许两个 Release，目标权重仅允许 0、5、25、50、100；所有变更均由具有项目管理权限的用户显式触发。

## 数据模型

### 观测连接

全局配置记录保存 Prometheus、Loki、Grafana 的 HTTPS 地址、是否启用和加密认证引用。凭据沿用平台 SecretCipher，普通响应和导出移除密文及哈希。Grafana 连接在本轮只用于健康/配置验证，不代理 Dashboard。

### 灰度策略

策略与平台网关路由关联，保存旧/新 Release ID、当前权重、目标权重、策略状态、版本和最后一次稳定失败原因。Release 必须属于同一服务部署、已经成功、且其运行时端口可被网关使用。

## API 与授权

- 观测连接 CRUD/测试：全局管理员。
- 项目观测摘要与日志摘要：项目查看权限加环境工作负载 Endpoint 权限。
- 灰度策略创建、详情、显式放量、回退：项目管理权限加网关及环境工作负载 Endpoint 权限。

所有写操作使用 ResourceVersion；连接凭据、上游原始错误、原始日志行中可能的凭据和内部拓扑不会进入审计或响应。

## 执行流

### 观测查询

1. handler 校验项目和 Endpoint 权限、模板、时间范围。
2. adapter 以 30 秒 context 调用上游 HTTP API。
3. adapter 限制序列、样本和日志行数，转换为稳定的摘要响应。
4. handler 在外部调用结束后写入只含模板、对象 ID、状态和稳定 reason 的审计记录。

### 灰度放量

1. handler 校验策略、允许的下一权重、候选 Release 和运行时健康。
2. 从成功 Release 快照生成旧/新 upstream，不接收用户提交的 Nginx 文本或地址。
3. renderer 生成含稳定分流键的 Nginx 配置；配置发布器进行候选写入、Nginx 预检、原子激活与 reload。
4. 发布成功后在事务内更新策略和审计；预检/reload 失败时发布器恢复旧配置，策略保持原权重。
5. 候选健康失败时将新版本降为 0%，保留旧流量并记录稳定失败原因。

## 测试与验收

- adapter fake 覆盖成功、超时、上游失败、响应超限和脱敏错误。
- handler 覆盖全局管理员、项目角色、Endpoint 权限、跨项目访问与审计。
- renderer 覆盖 0/5/25/50/100 分流、非法权重、确定性配置、候选 health 失败和 reload 恢复。
- 完成后运行平台 service、handler、datastore 专项测试、HTTP 编译、差异边界检查和敏感信息扫描。
- 每个子范围完成后按确认决策直接写入 Apifox main 分支并回读验证。
