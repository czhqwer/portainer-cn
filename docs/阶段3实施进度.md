### 2.2 V0.5 范围与排除项

唯一支持的输入为 Java 8 Jar、前端 dist ZIP、Docker image tar、OCI image archive，以及从受管 MinIO/S3 Compatible 读取的上述文件。每个成功路径的输出都是一个镜像；平台不保存源码、不编译源码，也不把原始制品直接作为运行时输入。

本阶段明确不实现中心 Nginx、域名、证书、网关切流、多 Docker 主机、跨主机分批发布、Kubernetes、Git、源码构建、用户 Dockerfile、用户 shell、内置 registry、完整 CI/CD、审批流、漏洞扫描、Python 源码包/wheel、SSR/Node 构建或独立阿里云 OSS adapter。阿里云 OSS 只允许在其 S3 Compatible endpoint 可用时接入；不能以独立 SDK 规避本边界。

### 2.3 文件、解压与类型识别契约

所有限额在服务端强制执行，Content-Type 只用于提示，不参与放行。限额使用实际流式读取字节数，而不是客户端声明的长度。

| 输入 | 原始文件上限 | 解压后上限 | 文件数上限 | 识别与必备条件 | 拒绝 reason |
| --- | ---: | ---: | ---: | --- | --- |
| Java 8 Jar | 1 GiB | 不适用 | 不适用 | ZIP/JAR 结构、存在 `META-INF/MANIFEST.MF`，且服务类型为 `java-service` | `ARTIFACT_TYPE_INVALID`、`ARTIFACT_SIZE_EXCEEDED` |
| 前端 dist ZIP | 512 MiB | 2 GiB | 50,000 | 安全 ZIP；SPA 必须有根 `index.html`，MPA/静态站点必须有受控入口 | `DIST_ENTRY_MISSING`、`ARCHIVE_UNSAFE` |
| Docker image tar | 10 GiB | 20 GiB | 50,000 | 受限 TAR，存在 Docker `manifest.json`、config 和合法 layer | `ARCHIVE_MANIFEST_INVALID`、`ARCHIVE_UNSAFE` |
| OCI image archive | 10 GiB | 20 GiB | 50,000 | 受限 TAR，存在 `oci-layout`、`index.json`、合法 manifest/config/layer | `ARCHIVE_MANIFEST_INVALID`、`ARCHIVE_UNSAFE` |

所有 archive/ZIP 校验器必须拒绝绝对路径、`..` 路径穿越、符号链接、硬链接、设备文件、稀疏文件、重复或超限条目、异常 layer 引用和解压大小超限；不能依赖解压工具的默认行为。校验、导入或包装失败时必须删除临时文件、临时解压目录和候选镜像，不能产生可部署 Artifact。

SHA256 始终对收到或下载的原始字节流计算，保存为小写 64 位十六进制。用户提供期望 SHA256 时必须精确匹配；不匹配即拒绝持久化和后续构建。`Traceability=strong` 至少要求原始 SHA256 或最终 digest；最终可部署 Artifact 必须同时记录原始 SHA256（适用时）、最终 image、标准 tag、digest、来源和模板/导入可追溯信息。

### 2.4 存储、凭据与保留契约

对象存储仅支持全局管理员管理的 `s3-compatible` 配置：endpoint、region、bucket、path prefix、TLS 选项和加密凭据元数据。access key、secret key、签名 URL 与服务器真实路径不得写入未加密 BoltDB 字段、API 响应、错误、审计、日志、toast 或测试快照；读取配置也必须返回脱敏 DTO。

`StoragePath` 仅可保存 provider 作用域内的逻辑对象键，绝不保存本机绝对路径、临时目录或签名 URL；普通 API 默认不返回它。临时文件地址只能驻留于进程内或受控临时目录，并在任务终止时清除。

原始制品的默认值是 `Retained=true`、`Cleanable=false`。只有构建/导入/推送终态成功、没有进行中制品任务、没有历史 Release/回滚/审计追溯引用且保留策略允许时，预检才可将其标记为可清理。清理只删除原始对象或本地原始文件并把 `Retained` 置为 false；不得删除 Artifact、Release、快照、SHA256、最终 tag/digest 或审计事实。

### 2.5 受控构建、tag 与状态契约

Jar 仅使用平台维护的 Java 8 基础镜像、固定工作目录 `/opt/app`、固定文件名 `app.jar` 与固定启动形式 `java <受限 JVM 参数> -jar /opt/app/app.jar <受限应用参数>`。dist 仅使用平台维护的静态 Nginx 基础镜像和生成的容器内站点配置；SPA 仅在容器内配置 `index.html` fallback，MPA/静态站点不注入 fallback。用户永远不能提供 Dockerfile、构建脚本、命令、基础镜像、任意 Nginx 配置或 Node/SSR 参数。

制品生命周期冻结为：`uploaded`/`fetched` → `validated` → `importing` 或 `building` → `built` → `pushing` → `ready`；任一失败进入 `failed`，记录脱敏 reason，只有显式重试才可开始新的任务。归档 Artifact 不得创建新任务或发布。构建、导入、推送分别拥有 Artifact 级任务锁；与 Release 锁独立，handler 事务只写入事实和锁，不在事务内做 Docker、对象存储或 registry I/O。

标准 tag 的唯一格式为 `<registry-namespace>/<project-slug>/<service-slug>:<artifact-version>-<artifact-id>`。namespace、project/service slug 与 version 都须按受限字符集规范化，冲突不能覆盖已有非本 Artifact tag，必须返回 `REGISTRY_TAG_CONFLICT`。push 成功且取得 digest 后才可进入 `ready`，再由既有 Release 预检和 `ReleaseExecutor` 使用该 image+digest。

统一 reason 至少包括：`ARTIFACT_TYPE_INVALID`、`ARTIFACT_SIZE_EXCEEDED`、`SHA256_MISMATCH`、`ARTIFACT_PERMISSION_DENIED`、`STORAGE_ACCESS_FAILED`、`STORAGE_OBJECT_NOT_FOUND`、`STORAGE_DOWNLOAD_TIMEOUT`、`ARCHIVE_UNSAFE`、`ARCHIVE_MANIFEST_INVALID`、`ARCHIVE_ARCHITECTURE_UNSUPPORTED`、`IMAGE_IMPORT_FAILED`、`CONTROLLED_BUILD_FAILED`、`REGISTRY_AUTH_FAILED`、`REGISTRY_TLS_FAILED`、`REGISTRY_PUSH_FAILED`、`REGISTRY_DIGEST_UNAVAILABLE`、`REGISTRY_TAG_CONFLICT`、`ARTIFACT_CLEANUP_BLOCKED` 和 `ARTIFACT_CLEANUP_FAILED`。reason 只表达场景，不能包含原始制品内容、凭据、真实路径或签名 URL。

### 2.6 API、权限与审计契约

后续批次在保持既有 `/api/platform` 风格的前提下，使用以下资源边界：

| 资源 | API | 服务端授权与限制 |
| --- | --- | --- |
| 存储配置 | `GET/POST /artifact-storages`、`GET/PUT/DELETE /artifact-storages/{id}`、`POST /artifact-storages/{id}/test` | 仅全局管理员；响应脱敏、凭据加密 |
| 手动上传 | `POST /artifacts/upload` | 项目制品写权限；归属、大小、类型、hash 和临时清理强校验 |
| 对象存储拉取 | `POST /artifacts/from-storage` | 已授权项目与受限 storage/path；不接受任意外部 URL |
| 准备镜像 | `POST /artifacts/{id}/prepare-image` | 项目制品写权限；Docker 动作还须 Endpoint 权限交集 |
| registry 推送 | `POST /artifacts/{id}/push` | 项目制品写权限与目标 Endpoint 权限交集；只允许受管 registry |
| 原始制品清理 | `POST /artifacts/{id}/cleanup-original` | 项目管理权限；先做引用预检 |
| 查询 | `GET /artifacts`、`GET /artifacts/{id}` | 项目可见性；默认脱敏，按项目/应用/服务/类型/来源/状态筛选 |

每次获取、校验、导入、构建、推送、清理和发布必须写入 `PlatformAuditLog`。审计摘要仅可使用 ID、文件名、类型、大小、SHA256、来源、模板版本、镜像引用、digest、状态与 reason；敏感数据只记录字段名称。发布继续保存不可变 ArtifactSnapshot、ConfigSnapshot 与 SecretSnapshots，失败不得改变当前线上 Release。

目标是让项目从全局管理员配置且显式授权的 MinIO/S3 Compatible 存储读取受支持制品；范围包括存储配置、连通性测试、受限对象浏览/手动相对路径、超时、大小、SHA256、脱敏和审计。依赖的批次 2 存储模型与批次 3 原子落盘管线已经完成，工作区开始时无用户并行改动。

### 5.2 完成内容

- 新增受管 `s3-compatible` adapter，复用仓库已有 AWS SDK，固定 path-style 调用以兼容 MinIO；支持 `HeadBucket` 连通测试、受限 `ListObjectsV2`、`HeadObject` 和流式 `GetObject`。每次外部调用都受一分钟 context timeout 控制，且不在 BoltDB 事务中执行。
- 新增仅全局管理员可用的存储配置列表、新建、更新和测试接口。access/secret key 在请求内使用已有 `SecretCipher` 加密后持久化；管理员和项目接口均使用脱敏 DTO，审计只记录敏感字段名、配置 ID、名称、provider、授权项目数量和结果。
- 存储配置新增显式 `AuthorizedProjectIds`。项目开发者/项目管理员只能取得已授权配置的选择列表，并只能在该配置的 path prefix 下浏览或拉取；服务端拒绝未授权配置、绝对路径、反斜杠和 `..` 路径穿越，并记录拒绝审计。
- 新增 `POST /api/platform/artifacts/from-storage`；同时保留 `/artifacts/object-storage` 兼容别名。下载先读取对象大小，再在批次 3 的受控临时目录中流式写入、计算 SHA256、校验类型/上限/期望 hash，并原子保存本地原始制品。对象 key 只作为逻辑 `SourcePath` 留在持久化追溯记录中，Artifact/Release 普通响应与审计不会暴露该 key 或本机路径。
- 拉取成功创建 `fetched` Artifact，失败不会保存 Artifact 或临时/最终半成品；增加 `artifact.fetched`、`artifact.fetch_failed` 和存储配置审计动作。下载实际字节数与 metadata 不一致时拒绝，超时、请求、大小、类型和 hash 均有脱敏 reason。
- 修复批次 2 密文字段的持久化语义：密文必须能写入已加密 BoltDB，不能使用会同时阻止持久化的 JSON 忽略标签；所有响应路径继续显式清空密文、CredentialHash、内部 StoragePath 与 SourcePath。Export/Import 自动化测试验证备份仍不导出任何凭据材料。
