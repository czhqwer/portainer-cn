# 阶段0平台核心模型与后端边界设计

版本：v1.3
日期：2026-07-11
关联文档：[私有化微服务部署平台产品需求文档](./私有化微服务部署平台产品需求文档.md)、[功能优先级与工作量排期](./功能优先级与工作量排期.md)

## 1. 设计目标

阶段 0 的目标是在进入阶段 1 编码前冻结平台地基，确保“已有镜像部署到 Docker 单机”可以先闭环，同时后续制品构建、中心 Nginx、多 Docker 主机和 Kubernetes 适配不需要推翻核心模型。

本版根据第二轮 CR 关闭以下 P0 细节：

- 修正 `ServiceDeployment.SpecRevision` 与 `LastDeployedSpecRevision` 的职责边界。
- 补齐嵌套 DTO、错误 reason、API 路由和数据字典到可编码粒度。
- 固定 Docker V0.1 的版本化容器命名、candidate 验证、旧容器保留和恢复流程。
- 补齐发布锁、幂等 payload 校验、租约续期、超时、取消和人工处置接口。
- 将健康结果定义为 `verified`、`startup-only`、`unverified` 三档，并限制 V0.1 可开放服务类型。
- 收紧 V0.1 最小审计范围，避免阶段 1 因审计需求过度膨胀。

阶段 0 不实现 Git 集成、源码构建、内置 registry、数据库实例创建、Kubernetes 部署、复杂审批流、漏洞扫描和完整 CI/CD。

## 2. 已确认决策

| 编号 | 决策 | 结论 |
| --- | --- | --- |
| ADR-001 | 版本口径 | V0.1 是 Docker 单机技术预览版；V0.5 是制品驱动版；V1.0 MVP 才包含网关、多主机、基础 RBAC 和结构化审计。 |
| ADR-002 | V0.1 发布安全 | 无中心网关时允许短暂停机；新版本启动、切换或健康检查失败时必须自动尝试恢复旧容器，并在 UI 标注不建议生产使用。 |
| ADR-003 | 服务跨环境模型 | 采用 `Application -> ServiceDefinition -> ServiceDeployment -> Release`，不再用多条 `Service + ServiceKey` 人工聚合跨环境服务。 |
| ADR-004 | 发布执行协议 | `POST /api/platform/releases` 返回 `202 + releaseId`，后台异步执行；同一 `ServiceDeployment` 同时只允许一个进行中的发布。 |
| ADR-005 | 幂等策略 | 创建发布必须携带 `Idempotency-Key`；同一用户、同一 `ServiceDeployment`、同一幂等键且 payload hash 相同，在有效期内返回同一 Release；payload 不同返回 409。 |
| ADR-006 | 审计模型 | 新增 `platform_audit_logs` 结构化审计表；现有 `UserActivityLog` 仅保留为通用活动日志。 |
| ADR-007 | 镜像不可变性 | 发布时尽量解析并保存 image digest；无法解析时允许发布但标记 `Traceability=weak`，人工回滚能力降级。 |
| ADR-008 | 适配器边界 | 拆分 `RuntimeDriver`、`DeploymentExecutor`、`GatewayAdapter`；`docker-container`、`docker-stack`、`kubernetes` 是不同 runtime driver。 |
| ADR-009 | 权限边界 | 平台项目权限与 Portainer Endpoint 访问权限取交集；平台不代替用户越权操作 Endpoint。V0.1 写操作限制管理员。 |
| ADR-010 | 容器命名 | V0.1 正式容器和 candidate 都使用 releaseId 版本化命名，平台通过 `CurrentServingReleaseID + RuntimeRef` 找当前容器，不依赖固定容器名。 |
| ADR-011 | 健康等级 | 发布后必须记录健康验证结果，分为 `verified`、`startup-only`、`unverified`；`IsProduction=true` 仅允许 `verified`。 |
| ADR-012 | 自动恢复表达 | V0.1 自动恢复是原 Release 内部步骤，不创建新的 auto-recover Release；人工选择历史版本回滚从阶段 2 起创建 rollback Release。 |
| ADR-013 | 配置模型 | `DesiredSpec` 中不直接保存最终环境变量事实，使用 `EnvOverrides` 和 `ConfigSet / ConfigEntry / EffectiveConfigSnapshot`，避免阶段 2 大迁移。 |

## 4. 核心关系

```text
Project
  ├─ PlatformEnvironment
  │   └─ DeploymentTarget -> Portainer Endpoint
  ├─ Application
  │   └─ ServiceDefinition
  │        └─ ServiceDeployment (ServiceDefinition x PlatformEnvironment)
  │             ├─ Artifact
  │             └─ Release
  ├─ ConfigSet
  └─ PlatformAuditLog
```

关系说明：

- `Project` 是最高业务组织单元，承载成员、环境、应用、配置和审计归属。
- `PlatformEnvironment` 是项目内的部署阶段，例如 `dev`、`test`、`prod`，通过 `DeploymentTarget.EndpointID` 绑定 Portainer Docker 环境。
- `Application` 是项目下的业务应用分组。
- `ServiceDefinition` 是跨环境复用的逻辑服务，例如“订单 API”。
- `ServiceDeployment` 是逻辑服务在某个环境中的部署配置和当前成功发布事实，例如“订单 API / prod”。
- `Artifact` 是部署输入，已有镜像、Jar、前端 dist、镜像 tar 都进入同一制品表。
- `Release` 是一次部署事实，保存制品、镜像、配置、目标、健康检查和恢复/回滚来源快照。

## 5. 核心模型设计

以下类型建议放在 `api/platform_models.go`，包名仍使用 `portainer`，保持与现有 `Endpoint`、`Registry`、`DatabaseConnection` 等模型一致。ID 类型继续使用 `int`。

### 5.1 通用字段与生命周期

所有平台主数据使用控制面生命周期字段，不把 Docker 实时运行态混入控制面状态。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `LifecycleStatus` | `active` / `archived` | 控制面状态，默认 `active` |
| `ArchivedAt` | `int64` | 归档时间，未归档为 0 |
| `ArchivedByUserID` | `UserID` | 归档人 |
| `CreatedAt` | `int64` | 创建时间 |
| `UpdatedAt` | `int64` | 更新时间 |
| `ResourceVersion` | `int` | 乐观锁版本，更新时必须匹配 |

归档规则：

- `Project`、`PlatformEnvironment`、`Application`、`ServiceDefinition`、`ServiceDeployment`、`Artifact` 默认逻辑归档，不物理删除。
- `Release` 永不删除，取消、失败、恢复失败都通过状态表达。
- 默认列表只返回 `active`，可通过 `includeArchived=true` 查询归档对象。
- 已归档对象的 `Slug` 默认不可复用，避免历史 Release 链接歧义。
- 归档父对象前必须检查活动子对象；例如归档 Project 前必须先归档环境、应用和服务部署。

V0.1 服务类型支持矩阵：

| 服务类型 | V0.1 是否开放 | 验证方式 | 说明 |
| --- | --- | --- | --- |
| `frontend` | 开放 | HTTP/TCP/startup-only | 仅已有镜像 |
| `static-site` | 开放 | HTTP/TCP/startup-only | 仅已有镜像；dist 构建进入 V0.5 |
| `backend` | 开放 | 推荐 HTTP/TCP | 适合长运行服务 |
| `python-service` | 条件开放 | HTTP/TCP/startup-only | 只支持已有长运行镜像，不支持源码包 |

| `worker` / `scheduler` / `python-job` | 隐藏 | 不适用 | candidate 启动可能重复消费任务，V0.1 不开放 |
| `database` / `redis` | 隐藏部署能力 | 不适用 | 只做绑定和展示，不创建实例 |

约束：

- 一个 `ServiceDefinition` 在同一个 Environment 下最多对应一个 active `ServiceDeployment`。
- `database` 和 `redis` 在 MVP 中仅作为连接绑定和展示对象，不负责创建实例。

### 5.6 ServiceDeployment

建议类型名：`PlatformServiceDeployment`
建议 ID：`PlatformServiceDeploymentID`

`ServiceDeployment` 保存用户期望配置和当前成功发布引用，不保存实时运行态。`SpecRevision` 只在影响部署的期望配置变更时递增，发布成功不会修改 `SpecRevision`。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `ID` | `PlatformServiceDeploymentID` | 主键 |
| `ProjectID` | `PlatformProjectID` | 冗余保存，便于查询和审计 |
| `EnvironmentID` | `PlatformEnvironmentID` | 所属环境 |
| `ApplicationID` | `PlatformApplicationID` | 所属应用 |
| `ServiceDefinitionID` | `PlatformServiceDefinitionID` | 逻辑服务 |
| `DesiredSpec` | `PlatformDeploymentDesiredSpec` | 期望部署配置 |
| `SpecRevision` | `int` | 影响部署的期望配置变更后递增，初始为 1 |
| `LastDeployedSpecRevision` | `int` | 最近成功发布实际使用的 `SpecRevision`，无成功发布时为 0 |
| `LastDeployedAt` | `int64` | 最近成功发布时间，无成功发布时为 0 |
| `CurrentServingReleaseID` | `PlatformReleaseID` | 当前对外服务 Release；允许状态为 `succeeded`，或 `resolved` 且 `ResolutionAction=accept-current` |
| `CurrentArtifactID` | `PlatformArtifactID` | 最近成功发布制品 |
| `CurrentRuntimeRef` | `RuntimeRef` | 最近成功运行资源引用，用于定位当前容器 |
| `CurrentImage` | `string` | 最近成功发布镜像引用，仅用于展示；事实以 Release 为准 |
| `DriftStatus` | `none` / `config-changed` / `runtime-missing` / `runtime-drifted` | 期望配置、发布快照和运行态差异 |
| `LastObservedAt` | `int64` | 最近一次观察运行态时间，可为 0 |
| 通用字段 | 见 5.1 | 生命周期和乐观锁 |

`PlatformDeploymentDesiredSpec` V0.1 字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `Image` | `PlatformImageSpec` | 期望镜像 |
| `Ports` | `[]PlatformPortSpec` | 容器端口与宿主机端口映射 |
| `EnvOverrides` | `[]PlatformEnvVar` | 服务环境级普通变量覆盖，不是最终有效配置事实 |
| `SecretRefs` | `[]PlatformSecretRef` | 敏感变量引用，阶段 2 完整启用 |
| `ConfigRefs` | `[]PlatformConfigRef` | 项目、环境、服务级配置引用 |
| `Volumes` | `[]PlatformVolumeSpec` | 挂载卷 |
| `HealthCheck` | `PlatformHealthCheckSpec` | 健康验证配置 |
| `Runtime` | `PlatformRuntimeSpec` | runtime driver、保留策略和停止超时 |

事实来源规则：

- 用户期望配置以 `DesiredSpec + SpecRevision` 为准。
- 当前对外服务版本以 `CurrentServingReleaseID` 指向的 `Release` 为准。
- 自动发布成功时在同一事务内更新 `CurrentServingReleaseID`、`CurrentArtifactID`、`CurrentRuntimeRef`、`CurrentImage`、`LastDeployedSpecRevision`、`LastDeployedAt` 和 `DriftStatus`。
- 发布成功不修改 `SpecRevision`。
- 实时运行态由 Docker 查询或后续调和器写入观察结果，不用 `ServiceDeployment` 生命周期表达。
- `CurrentImage` 只做列表展示缓存，不能作为回滚依据。
### 5.7 配置模型预留

阶段 0 先固定三级配置模型，阶段 2 再开放完整 UI 和敏感变量管理，避免把 `DesiredSpec.Env` 迁移成配置中心时返工。

`PlatformConfigSet`：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `ID` | `PlatformConfigSetID` | 主键 |
| `ProjectID` | `PlatformProjectID` | 所属项目 |
| `ScopeType` | `project` / `environment` / `service-deployment` | 配置作用域 |
| `ScopeID` | `int` | 对应作用域 ID |
| `Name` | `string` | 配置集名称，默认 `default` |
| `Entries` | `[]PlatformConfigEntry` | 配置项 |
| `Revision` | `int` | 配置集版本 |
| 通用字段 | 见 5.1 | 生命周期和乐观锁 |

`PlatformConfigEntry`：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `Key` | `string` | 环境变量名，匹配 `^[A-Z_][A-Z0-9_]*$` |
| `ValueType` | `plain` / `secret-ref` / `database-ref` / `redis-ref` | 值类型 |
| `Value` | `string` | 普通值或引用 ID；敏感值不保存明文 |
| `Sensitive` | `bool` | 是否敏感 |
| `Required` | `bool` | 发布前是否必须有有效值 |
| `Source` | `project` / `environment` / `service-deployment` | 发布快照中的来源层级 |

`EffectiveConfigSnapshot`：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `SpecRevision` | `int` | 发布使用的部署配置版本 |
| `ConfigSetRevisions` | `map[string]int` | 每个作用域配置集版本 |
| `Entries` | `[]PlatformConfigEntrySnapshot` | 合并后的有效变量 |
| `Hash` | `string` | 规整化后 hash，用于漂移检测 |

合并顺序：项目级 < 环境级 < 服务部署级 `EnvOverrides`。后层覆盖前层；敏感值默认只在部署注入时解密，API 和审计均脱敏。

### 5.8 Artifact

### 6.2 ReleaseLock

建议类型名：`PlatformReleaseLock`
建议 key：`ServiceDeploymentID`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `ID` | `string` | 可使用 `ServiceDeploymentID` 字符串 |
| `ServiceDeploymentID` | `PlatformServiceDeploymentID` | 被锁定的服务环境部署 |
| `ReleaseID` | `PlatformReleaseID` | 当前持锁 Release |
| `IdempotencyKeyHash` | `string` | 幂等键 hash |
| `PayloadHash` | `string` | 创建 payload hash，用于发现重复键不同请求 |
| `LeaseOwner` | `string` | worker 实例 ID |
| `LeaseExpiresAt` | `int64` | 租约过期时间 |
| `CreatedAt` | `int64` | 创建时间 |
| `UpdatedAt` | `int64` | 更新时间 |

规则：

- 创建发布时在 BoltDB 事务内检查 active lock 和幂等记录。
- 同一 `Idempotency-Key` 且 payload hash 相同，24 小时内返回同一 Release。
- 同一 `Idempotency-Key` 但 payload hash 不同，返回 `409 PLATFORM_IDEMPOTENCY_PAYLOAD_MISMATCH`。
- 不同幂等键但同一 `ServiceDeployment` 已有进行中发布，返回 `409 PLATFORM_RELEASE_CONFLICT`。
- `succeeded`、`failed`、`canceled` 必须自动释放锁；`failed` 包括旧容器已成功恢复的失败发布。`recovery-failed` 和 `interrupted` 默认继续持锁，直到 `resolve`、恢复重试成功，或管理员明确执行 `release-lock-only`。`resolved` 必须释放锁。
- 启动恢复扫描发现锁对应 Release 已终态但锁未释放时，先写审计再释放；非终态且 lease 过期时进入恢复流程。

### 6.3 不进入 datastore 的内容

- Docker 容器实时状态、日志、stats。
- registry 凭据明文。
- 对象存储 access key / secret key 明文。
- 敏感变量明文。
- Nginx 当前运行配置全文；阶段 4 只保存平台生成配置快照和 hash。

## 7. 后端 API 边界

### 7.1 分层

```text
api/http/handler/platform
  只负责路由、payload 校验、响应、HTTP 错误转换、调用平台服务。
api/platform
  平台业务服务，负责模型一致性、权限判定、审计事件。
api/platform/release
  发布服务，负责异步任务、状态机、锁、幂等和恢复。
api/platform/deploy
  RuntimeDriver、DeploymentExecutor、GatewayAdapter 接口。
api/platform/deploy/dockercontainer
  Docker container runtime driver，复用 dockerclient.ClientFactory。
api/dataservices/platform*
  BoltDB 持久化服务。
```

handler 不直接创建 Docker client，不直接写多个 datastore bucket。部署行为统一进入发布服务，再由发布服务调用 executor 和 runtime driver。

### 7.2 通用约定

响应 envelope：

```json
{
  "data": {},
  "meta": {
    "requestId": "req_..."
  }
}
```

分页响应：

```json
{
  "data": [],
  "pagination": {
    "page": 1,
    "pageSize": 20,
    "total": 100
  }
}
```

错误响应：

```json
{
  "code": "PLATFORM_VALIDATION_FAILED",
  "message": "发布校验失败",
  "details": {
    "reason": "PORT_CONFLICT",
    "field": "Ports[0].HostPort"
  },
  "requestId": "req_..."
}
```

通用错误码：

| code | HTTP | 说明 |
| --- | --- | --- |
| `PLATFORM_NOT_FOUND` | 404 | 对象不存在或无权查看 |
| `PLATFORM_FORBIDDEN` | 403 | 有对象但无操作权限 |
| `PLATFORM_VALIDATION_FAILED` | 400 | payload 或业务校验失败，使用 `details.reason` 表示场景 |
| `PLATFORM_RESOURCE_VERSION_CONFLICT` | 409 | 乐观锁冲突 |
| `PLATFORM_RELEASE_CONFLICT` | 409 | 同一 `ServiceDeployment` 已有进行中发布 |
| `PLATFORM_IDEMPOTENCY_PAYLOAD_MISMATCH` | 409 | 相同幂等键提交了不同 payload |
| `PLATFORM_RUNTIME_UNAVAILABLE` | 503 | Endpoint / Docker / Agent 不可用 |
| `PLATFORM_UNSUPPORTED_OPERATION` | 400 | 当前阶段或服务类型不支持 |

异步发布超时不使用 HTTP `504`。超时体现为 Release 状态、步骤 `Reason=TIMEOUT` 和审计事件；`GET /releases/{id}` 返回 200。

### 7.3 场景级 reason 与前端提示

| reason | 典型 code | 前端提示方向 |
| --- | --- | --- |
| `PORT_CONFLICT` | `PLATFORM_VALIDATION_FAILED` | 宿主机端口已被占用，提示更换端口或释放占用进程 |

| `RUNTIME_STOP_FAILED` | Release step | 旧容器停止失败，切换中止并清理 candidate |
| `INTERRUPTED` | Release step | Portainer 进程中断或租约丢失，需恢复扫描判定 |
| `TIMEOUT` | Release step | 后台步骤超时，展示阶段、默认超时和补偿动作 |
| `RECOVERY_FAILED` | Release step | 旧容器恢复失败，需要人工处置 |
| `UNSUPPORTED_SERVICE_TYPE` | `PLATFORM_UNSUPPORTED_OPERATION` | 当前 V0.1 不开放该服务类型部署 |
| `IDEMPOTENCY_PAYLOAD_MISMATCH` | `PLATFORM_IDEMPOTENCY_PAYLOAD_MISMATCH` | 重复请求键对应不同内容，要求刷新后重新提交 |

## 8. 发布执行模型

### 8.1 状态机

| 状态 | 可进入来源 | 可迁移到 | 说明 |
| --- | --- | --- | --- |
| `queued` | 创建发布 | `validating` / `canceled` | 已落库，等待 worker |
| `validating` | `queued` | `pulling` / `failed` / `canceled` | 校验模型、权限、Endpoint、端口、镜像 |
| `pulling` | `validating` | `preparing` / `failed` / `canceled` | 拉取镜像、解析 digest |
| `preparing` | `pulling` | `candidate-starting` / `failed` / `canceled` | 生成容器配置，创建 candidate |
| `candidate-starting` | `preparing` | `candidate-checking` / `recovering` / `failed` | 启动 candidate |
| `candidate-checking` | `candidate-starting` | `switching` / `recovering` / `failed` | 临时端口健康验证 |
| `switching` | `candidate-checking` | `final-checking` / `recovering` | 停旧容器、启动新正式容器，V0.1 可能短暂停机 |
| `final-checking` | `switching` | `succeeded` / `recovering` | 正式容器健康验证 |
| `recovering` | 任意部署失败状态 | `failed` / `recovery-failed` | 尝试恢复旧容器 |
| `interrupted` | 进程重启恢复 | `failed` / `recovery-failed` / `resolved` | worker 租约过期后由恢复流程判定 |
| `succeeded` | `final-checking` | 终态 | 更新 `ServiceDeployment` 当前成功发布 |
| `failed` | 多状态 | 终态 | 失败但无需人工处置，旧版本已恢复或无旧版本 |
| `recovery-failed` | `recovering` | `recovering` / `resolved` | 旧容器恢复失败，需人工处置；默认继续持锁 |
| `canceled` | `queued` / `validating` / `pulling` / `preparing` | 终态 | 已取消；进入 Docker 切换后不保证立即取消 |
| `resolved` | `interrupted` / `recovery-failed` | 终态 | 管理员人工确认已处理，并按 `ResolutionAction` 释放锁或接纳当前运行版本 |

合法迁移由发布服务集中校验，handler 不能直接改 Release 状态。

### 8.2 任务执行策略表

| 阶段 | 默认 timeout | Lease TTL | Heartbeat | 可取消点 | 超时补偿动作 |
| --- | --- | --- | --- | --- | --- |
| `queued` | 10 分钟 | 无 | 无 | 是 | 标记 `failed`，reason=`TIMEOUT` |
| `validating` | 2 分钟 | 2 分钟 | 30 秒 | 是 | 标记 `failed`，不创建 Docker 资源 |
| `pulling` | 10 分钟 | 2 分钟 | 30 秒 | 是 | 标记 `failed`，reason=`IMAGE_PULL_FAILED` 或 `TIMEOUT` |
| `preparing` | 2 分钟 | 2 分钟 | 30 秒 | 是 | 标记 `failed`，清理已创建但未启动资源 |
| `candidate-starting` | 2 分钟 | 2 分钟 | 30 秒 | 否 | 停止并删除 candidate，标记 `failed` 或进入 `recovering` |
| `candidate-checking` | `StartPeriod + Retries * Interval`，默认 60 秒 | 2 分钟 | 30 秒 | 否 | 清理 candidate，旧容器保持运行，标记 `failed` |
| `switching` | 60 秒 | 2 分钟 | 15 秒 | 否 | 进入 `recovering`，尝试恢复旧容器 |
| `final-checking` | 120 秒 | 2 分钟 | 15 秒 | 否 | 停新容器，进入 `recovering` |
| `recovering` | 120 秒 | 2 分钟 | 15 秒 | 否 | 恢复失败时标记 `recovery-failed`，保留全部 RuntimeRef |
| `cleanup-runtime` | 5 分钟 | 2 分钟 | 30 秒 | 否 | 清理失败写入步骤，保留人工提示 |

规则：

- `queued` 没有 lease，由队列 watchdog 按 `QueueExpiresAt` 或 `CreatedAt + 10 分钟` 扫描超时任务，避免 worker 不可用时永久停留在 queued。
- worker 领取任务时写入 `LeaseOwner` 和 `LeaseExpiresAt`，执行期间按表续租。
- 安全取消点只覆盖 `queued`、`validating`、`pulling`、`preparing`；进入 `candidate-starting` 后取消请求只记录，worker 继续走到安全终态。
- 进入 `switching` 后不得直接取消，必须在 `succeeded`、`failed`、`recovery-failed` 或 `interrupted` 中结束。
- 后台超时只更新 Release 和步骤，不返回 HTTP `504`。

### 8.3 BoltDB 与 Docker 副作用顺序

1. BoltDB 事务创建 Release、ReleaseLock、审计 pending 事件。
2. worker 领取 Release，写入 `LeaseOwner` 和 `LeaseExpiresAt`。
3. 每个 Docker 副作用前先写入即将执行的 step。
4. Docker 副作用完成后立即写入 step 结果和 runtime ref。
5. 最终成功时，在同一 BoltDB 事务内更新 Release、`ServiceDeployment` 当前成功发布、释放锁、写审计。
6. 如果 Docker 成功但 BoltDB 最终更新失败，启动恢复流程，通过容器 label 与 Release step 对账，标记 `interrupted` 或补写 runtime ref，页面提示需要人工确认。

### 8.4 重启恢复与孤儿清理

Portainer 启动时执行恢复扫描：

- 找到 `queued` 且超过 `QueueExpiresAt` 的 Release，由队列 watchdog 标记 `failed`，reason=`TIMEOUT`。
- 找到 `validating` 到 `recovering` 中 `LeaseExpiresAt` 过期的 Release，进入恢复扫描。
- 按 Release runtime snapshot 和 Docker label 查找 candidate、新正式容器、旧容器。
- candidate 孤儿容器默认停止并删除。
- 如果新正式容器已成功且健康检查通过，但 Release 未 `succeeded`，标记 `interrupted` 并提示人工确认，不自动推进为成功。
- 如果旧容器仍存在且新容器失败，尝试恢复旧容器。
- 无法判断时标记 `recovery-failed` 和 `ManualActionRequired=true`。
- 扫描发现 `succeeded`、`failed`、`canceled`、`resolved` 已终态但 ReleaseLock 未释放时，写审计并释放锁；`recovery-failed` 和 `interrupted` 不自动释放。

### 8.5 人工处置接口

| 接口 | 适用状态 | 行为 |
| --- | --- | --- |
| `POST /releases/{id}/resolve` | `interrupted` / `recovery-failed` | 管理员选择 `accept-current`、`mark-handled` 或 `release-lock-only`；写审计并释放锁 |
| `POST /releases/{id}/retry-recovery` | `recovery-failed` / `interrupted` | 使用 `RuntimeSnapshot.PreviousRuntimeRef` 再次尝试恢复旧容器；重试前必须校验 `ServiceDeployment.CurrentRuntimeRef` 未被其他处置改变 |
| `POST /releases/{id}/cleanup-runtime` | `failed` / `recovery-failed` / `interrupted` | 清理 candidate、失败的新正式容器或超出保留策略的旧容器 |

`resolve` payload 草案：

```json
{
  "Action": "accept-current",
  "Comment": "容器已人工验证可用，接纳为当前版本"
}
```

`accept-current` 只允许在管理员确认当前 Docker 资源健康且与 Release 快照匹配时使用；服务会把 Release 置为 `resolved`，设置 `ResolutionAction=accept-current`，并同步更新 `ServiceDeployment.CurrentServingReleaseID`、`CurrentArtifactID`、`CurrentRuntimeRef`、`CurrentImage`、`LastDeployedSpecRevision`、`LastDeployedAt` 和 `DriftStatus`。`mark-handled` 与 `release-lock-only` 不得写入 `CurrentServingReleaseID`。

## 9. V0.1 Docker 单机发布方案

### 9.1 安全承诺

V0.1 无中心 Nginx 网关，固定宿主机端口切换不能承诺零停机。阶段 1 验收承诺如下：

- 允许短暂停机，默认目标中断窗口不超过 60 秒。
- 新版本失败后自动尝试恢复旧容器，默认恢复目标不超过 120 秒。
- 恢复失败必须标记 `recovery-failed`，展示旧容器、新容器、端口、错误日志和人工处置建议。
- 生产环境部署前必须二次确认，并显示“不建议生产使用”。

### 9.2 版本化容器命名与 RuntimeRef

V0.1 不使用固定正式容器名。Docker 停止旧容器不会释放容器名，若复用固定名创建新容器会失败，因此容器名必须包含 releaseId。

命名规则：

```text
正式容器：pcn-{projectSlug}-{envSlug}-{serviceSlug}-r{releaseId}
candidate：pcn-{projectSlug}-{envSlug}-{serviceSlug}-r{releaseId}-candidate
```

RuntimeRef 规则：

- 当前线上容器由 `ServiceDeployment.CurrentServingReleaseID + CurrentRuntimeRef` 定位。
- 每个容器写入 label：`com.portainer-cn.platform.project`、`environment`、`service-deployment-id`、`release-id`、`runtime-role=current|candidate|previous`。
- 发布成功后旧容器默认保留最近 1 个成功版本或 7 天，以先到者为准；超过策略由清理任务或人工 `cleanup-runtime` 清理。
- 恢复旧版本时优先直接重启 `PreviousRuntimeRef` 指向的旧容器；若旧容器被删除，标记 `recovery-failed`。

candidate 与正式容器配置一致性：

- candidate 和正式容器使用完全相同的 image、digest、env、secret refs、volume、network、restart policy、command、entrypoint、labels。
- 差异只允许存在于容器名、runtime role label 和端口绑定：candidate 使用随机宿主机端口，正式容器使用用户配置的正式端口。
- 如果服务使用共享可写卷，UI 必须提示 candidate 可能产生写入副作用；V0.1 不开放 worker、scheduler、job 等可能重复消费任务的类型。

### 9.3 candidate 健康验证

- candidate 优先使用 Docker 随机宿主机端口，不占用正式端口。
- 发布服务通过 `Environment.HealthCheckHost` 或 `Target.HostAddress` 访问临时端口。
- 不再默认假设 `127.0.0.1` 可访问宿主机端口；容器化 Portainer 中 `127.0.0.1` 指向 Portainer 容器自身。
- 本地 Docker socket、容器化 Portainer、本地 Agent、远程 Agent 的可达地址必须由技术 Spike 验证后定最终默认策略。
- 如果用户选择 `verified` 但无法访问 candidate 临时端口，发布前校验失败；系统不得在运行时静默降级。用户需要配置 `HealthCheckHost`，或返回向导显式选择 `startup-only` 后重新提交；`IsProduction=true` 仅允许 `verified`。

健康结果：

| 等级 | 成功标准 | 适用 |
| --- | --- | --- |
| `verified` | HTTP/TCP 检查通过 | 推荐所有 HTTP/TCP 服务使用，生产环境默认要求 |
| `startup-only` | 容器持续运行到 `StartPeriodSeconds`，未退出 | 仅 V0.1 非生产环境可用，需强警告，不得自动降级 |
| `unverified` | 无可用检查，仅记录未验证 | V0.1 非生产可临时允许，不得宣称健康发布；生产环境禁止 |

### 9.4 替换流程

1. 校验旧容器 `PreviousRuntimeRef`、正式端口和服务类型。
2. 拉取镜像并解析 digest。
3. 创建版本化 candidate 容器，使用随机宿主机端口。
4. 执行 candidate 健康验证或 startup-only 验证。
5. 保存 candidate 日志、验证结果和 inspect 摘要，然后停止并删除 candidate，避免与正式容器并行运行。
6. 记录旧容器 inspect 摘要和 runtime ref。
7. 停止旧容器，释放正式端口。
8. 创建版本化正式新容器，绑定正式端口。
9. 执行正式健康验证。
10. 成功后更新 `ServiceDeployment.CurrentServingReleaseID`、`CurrentRuntimeRef`、`LastDeployedSpecRevision`、`LastDeployedAt` 和 `DriftStatus`。
11. 根据保留策略保留旧容器，供自动恢复或人工诊断。
12. 失败时停止新容器，重启旧容器；恢复失败进入 `recovery-failed` 并继续持锁。

### 9.5 失败补偿矩阵

| 失败点 | 对旧版本影响 | 补偿动作 | 终态 | reason |
| --- | --- | --- | --- | --- |
| 模型校验失败 | 无影响 | 不创建 Docker 资源 | `failed` | `PLATFORM_VALIDATION_FAILED` 对应 reason |
| 服务类型不支持 | 无影响 | 阻止提交 | `failed` | `UNSUPPORTED_SERVICE_TYPE` |
| 端口冲突 | 无影响 | 不创建 Docker 资源 | `failed` | `PORT_CONFLICT` |
| 镜像拉取失败 | 无影响 | 记录 registry / image 错误 | `failed` | `IMAGE_PULL_FAILED` / `REGISTRY_AUTH_FAILED` |
| candidate 启动失败 | 无影响 | 删除 candidate | `failed` | `RUNTIME_START_FAILED` |
| candidate 健康失败 | 无影响 | 删除 candidate | `failed` | `HEALTHCHECK_FAILED` |
| candidate 地址不可达 | 无影响 | 删除 candidate，提示配置 `HealthCheckHost` 或返回向导显式选择 `startup-only` 后重试 | `failed` | `HEALTHCHECK_HOST_UNREACHABLE` |
| 停旧容器失败 | 旧版本可能仍运行 | 中止切换，清理 candidate | `failed` | `RUNTIME_STOP_FAILED` |
| 正式容器创建失败 | 旧容器已停 | 重启旧容器 | `failed` 或 `recovery-failed` | `RUNTIME_START_FAILED` |
| 正式健康失败 | 新容器已占端口 | 停新容器，重启旧容器 | `failed` 或 `recovery-failed` | `HEALTHCHECK_FAILED` |
| 旧容器恢复失败 | 服务可能不可用 | 标记人工处置，保留全部 RuntimeRef | `recovery-failed` | `RECOVERY_FAILED` |
| worker 超时 | 状态未定 | 恢复扫描按 RuntimeRef 对账 | `interrupted` / `failed` / `recovery-failed` | `TIMEOUT` |
| Portainer 进程中断 | 状态未知 | 启动恢复扫描，对账 Docker labels | `interrupted` / `failed` / `recovery-failed` | `INTERRUPTED` |

### 9.6 Docker/Agent 技术 Spike

阶段 1 编码前必须完成以下 Spike 并把结论回填到本设计或实现 ADR：

| 场景 | 必验问题 | 通过标准 |
| --- | --- | --- |
| Portainer 后端直接运行在宿主机 + Docker socket | candidate 随机宿主机端口访问方式 | 后端可通过配置或自动推断访问 candidate |
| 容器化 Portainer + Docker socket | `127.0.0.1` 不可用时的宿主机地址 | 通过 `HealthCheckHost`、Docker bridge gateway 或明确配置访问 candidate |
| 本地 Agent | 后端到 Agent 目标宿主机随机端口可达性 | 能完成 candidate 检查，或明确要求用户显式选择 startup-only 后重试 |
| 远程 Agent | 跨主机网络与防火墙 | 健康检查失败时 reason 为 `HEALTHCHECK_HOST_UNREACHABLE`，页面提示可配置地址 |
| 版本化容器命名 | 旧容器停止后新容器创建 | 不再出现固定容器名冲突 |
| 正式端口切换 | 停旧、启新、恢复旧 | 失败时可重启旧容器并记录中断时间 |
| 私有 registry | 拉取认证和 digest 解析 | 凭据错误返回 `REGISTRY_AUTH_FAILED`，拉取失败返回 `IMAGE_PULL_FAILED` |

未完成 Spike 前，不进入 Docker 发布执行器正式编码。

## 10. 部署适配器边界

### 10.1 RuntimeDriver

```go
type RuntimeDriver interface {
    ID() RuntimeDriverID // docker-container, docker-stack, kubernetes
    Validate(ctx context.Context, req RuntimeRequest) (*ValidationResult, error)
    Prepare(ctx context.Context, req RuntimeRequest) (*PreparedRuntime, error)
    DeployCandidate(ctx context.Context, prepared PreparedRuntime) (*RuntimeRef, error)
    Switch(ctx context.Context, prepared PreparedRuntime, candidate RuntimeRef, previous *RuntimeRef) (*RuntimeRef, error)
    Recover(ctx context.Context, req RecoverRequest) (*RecoverResult, error)
    Cleanup(ctx context.Context, req CleanupRequest) (*CleanupResult, error)
    Status(ctx context.Context, ref RuntimeRef) (*RuntimeStatus, error)
    Logs(ctx context.Context, ref RuntimeRef, opts LogOptions) (io.ReadCloser, error)
    Restart(ctx context.Context, ref RuntimeRef) error
    Stop(ctx context.Context, ref RuntimeRef) error
}
```

`RuntimeDriver.ID()` 必须区分到具体 runtime：`docker-container`、`docker-stack`、`kubernetes`，不能只返回 Docker/Kubernetes 大类。

### 10.2 DeploymentExecutor

`DeploymentExecutor` 负责编排单目标、多目标和分批发布，不直接调用 Docker API。V0.1 只实现 `SingleTargetExecutor`；阶段 5 增加 `BatchExecutor`。

```go
type DeploymentExecutor interface {
    Mode() ExecutorMode // single, multi, batch
    Execute(ctx context.Context, releaseID portainer.PlatformReleaseID) error
    Cancel(ctx context.Context, releaseID portainer.PlatformReleaseID) error
    Recover(ctx context.Context, releaseID portainer.PlatformReleaseID) error
}
```

### 10.3 GatewayAdapter

```go
type GatewayAdapter interface {
    Validate(ctx context.Context, req GatewayRequest) (*ValidationResult, error)
    Render(ctx context.Context, req GatewayRequest) (*GatewayPlan, error)
    Apply(ctx context.Context, plan GatewayPlan) (*GatewayResult, error)
    Rollback(ctx context.Context, snapshot portainer.PlatformGatewaySnapshot) error
}
```

V0.1 不启用 `GatewayAdapter`。阶段 4 固定使用独立 `GatewayAdapter`，不把网关切流塞进 `RuntimeDriver` 的 promote / switch 逻辑。

## 11. 权限与审计

### 11.1 角色优先级

- 全局管理员拥有全部平台能力。
- 用户项目角色优先于团队项目角色。
- 多个团队角色取权限最高者。
- 平台项目权限与 Portainer Endpoint 权限取交集；无 Endpoint 访问权限时，即使有项目权限也不能部署、看日志或读运行态。
- 越权访问存在但无权的对象，读请求返回 404；明确操作已知对象但权限不足时返回 403。

### 12.3 阶段 1 主流程

```text
项目列表
  -> 创建/选择项目
  -> 创建/选择环境并绑定 Docker Endpoint
  -> 创建/选择应用
  -> 创建/选择逻辑服务
  -> 创建/选择环境部署配置

  -> 填写端口、EnvOverrides、健康验证等级
  -> 部署前校验

  -> 发布详情轮询状态
  -> 服务详情查看状态、日志、RuntimeRef 和漂移提示
```

部署向导至少包含以下步骤：

1. 基本信息。
2. 制品来源，V0.1 仅已有镜像地址。
3. 镜像与 registry 拉取认证。
4. 端口与健康验证。
5. 环境变量和配置覆盖。
6. 发布策略，V0.1 固定 replace。
7. 校验结果。
8. 确认并发布。

### 12.4 页面状态

阶段 1 必须设计并实现：

- 空状态：无项目、无环境、无应用、无服务、无发布。
- 无权限：隐藏不可用操作，直接访问返回权限提示。
- 校验失败：端口冲突、镜像拉取失败、Endpoint 离线、健康检查地址不可达、服务类型不支持。
- 发布中：展示当前步骤、耗时、lease 状态和可取消状态。
- 健康检查失败：展示 candidate 或正式容器日志摘要、恢复状态。
- 恢复失败：展示人工处置入口、RuntimeRef、旧容器和新容器状态。
- 运行资源丢失：容器被外部删除时，提示重新部署或手动修复。
- 弱可追溯：镜像 digest 未解析时，提示 tag 可变导致回滚能力降级。
- 生产环境确认：V0.1 部署到 `IsProduction=true` 环境时，提示允许短暂停机且不建议生产使用。
- startup-only / unverified：展示验证等级，不把 `unverified` 文案写成健康发布。

## 13. 阶段 1 验收用例

| 用例 | 期望 |
| --- | --- |
| 创建完整项目链路 | 项目、环境、应用、逻辑服务、环境部署配置创建成功 |
| 公开镜像发布成功 | Release 到 `succeeded`，服务详情显示 RuntimeRef、容器和日志 |
| 私有镜像发布成功 | 使用 Portainer registry 凭据拉取成功，并尽量保存 digest |
| 私有镜像凭据错误 | 发布校验或拉取失败，reason=`REGISTRY_AUTH_FAILED`，旧容器不受影响 |
| 镜像拉取失败 | Release failed，reason=`IMAGE_PULL_FAILED`，旧容器不受影响 |
| 端口冲突 | 发布校验失败，reason=`PORT_CONFLICT` |
| 不支持服务类型 | V0.1 阻止提交，reason=`UNSUPPORTED_SERVICE_TYPE` |
| candidate 健康失败 | candidate 被清理，旧容器保持运行，reason=`HEALTHCHECK_FAILED` |
| candidate 地址不可达 | 失败 reason=`HEALTHCHECK_HOST_UNREACHABLE`，提示配置 `HealthCheckHost` 或返回向导显式选择 `startup-only` 后重试 |
| 正式容器健康失败 | 新容器停止，旧容器恢复，Release failed |
| 旧容器恢复失败 | Release `recovery-failed`，标记人工处置并继续持锁，直到 `resolve` 或恢复重试成功 |
| 相同幂等键重复点击 | payload 相同返回同一 releaseId |
| 相同幂等键不同 payload | 返回 `409 PLATFORM_IDEMPOTENCY_PAYLOAD_MISMATCH` |
| 并发发布 | 第二个请求返回 `PLATFORM_RELEASE_CONFLICT` |
| 任务超时 | `GET Release` 返回 200，步骤 reason=`TIMEOUT` |
| Portainer 重启 | stuck release 被标记 `interrupted` 或进入恢复流程，candidate 孤儿可清理 |
| 外部删除容器 | 服务详情显示 `runtime-missing` |
| 非管理员访问平台接口 | V0.1 返回 403 或 404；发布相关拒绝写最小审计，非发布类拒绝不作为 Gate |
| 人工接纳当前容器 | `resolve` 写审计，设置 `ResolutionAction=accept-current`，同步更新当前服务版本缓存，Release 终态为 `resolved` |

## 14. 阶段0 Gate 结论清单

阶段 0 拆成两个 Gate：

### 14.1 Gate 0A：文档与模型冻结

本轮修订后可作为有条件通过，允许启动：模型、dataservice、CRUD API、异步发布状态机框架和前端页面骨架。

必须确认：

- PRD、排期和设计文档中的 V0.1 / V0.5 / V1.0 口径一致。
- `ServiceDefinition / ServiceDeployment` 拆分冻结。
- `CurrentServingReleaseID`、`SpecRevision`、`LastDeployedSpecRevision`、`LastDeployedAt` 字段职责冻结。
- 嵌套 DTO、错误 reason、API 路由、ReleaseLock、queued watchdog 和人工处置接口足以编码。
- V0.1 所有 `/api/platform` 业务接口限制管理员访问。
- V0.1 健康等级和服务类型支持矩阵冻结，生产环境只允许 `verified`。
- V0.1 最小审计范围冻结，非发布类 denied 审计不扩大阶段 1 Gate。
- 前端 IA 和阶段 1 验收用例足以支持前后端并行。

### 14.2 Gate 0B：Docker/Agent Spike

发布执行器正式编码前必须完成并回填结论：

- 容器化 Portainer + Docker socket 下的 candidate 可达地址策略。
- 本地 Agent 与远程 Agent 的随机端口探测策略。
- candidate 验证后停止/删除，再切换正式容器的端口释放流程。
- 私有 registry 拉取认证和 digest 解析策略。
- 旧容器恢复、`recovery-failed` 持锁和人工 `resolve` 操作验证。

Gate 0A 通过后可以启动阶段 1 的模型、CRUD、异步框架和前端工作；Docker 发布执行器必须等待 Gate 0B 通过。
