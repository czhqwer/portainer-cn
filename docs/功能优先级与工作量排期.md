# 功能优先级与工作量排期

版本：v1.0  
日期：2026-07-09  
关联文档：[私有化微服务部署平台产品需求文档](./私有化微服务部署平台产品需求文档.md)

## 1. 排期目标

本文档基于私有化微服务部署平台 PRD，梳理功能优先级、开发阶段、工作量估算、关键依赖和阶段验收标准。

排期目标不是一次性完成完整平台，而是按风险和依赖关系分阶段交付：

1. 先跑通“已有镜像部署到 Docker 单机”的最小闭环。
2. 再补齐配置、回滚、审计等部署平台基础能力。
3. 然后扩展制品上传、MinIO 拉取、Java Jar 和前端 dist 构建。
4. 最后补充 Nginx 网关、多 Docker 主机、分批发布和增强能力。

## 2. 排期假设

### 2.1 人员假设

默认按 1 到 2 名主要开发者估算。

如果只有 1 名开发者，排期应按上限估算；如果前后端可并行，部分阶段可压缩 20% 到 30%。

### 2.2 技术假设

- 基于当前 Portainer 二开仓库继续开发。
- 首期只支持 Docker 单机和多 Docker 主机。
- 开发测试阶段优先 Docker 单机。
- 后续 Kubernetes 作为下一阶段目标，不进入当前主排期。
- 不集成 Git，不拉取源码。
- 最终运行物统一为镜像。
- 私有镜像仓库只接入已有 registry。
- 对象存储以 MinIO 为主，同时兼容阿里云 OSS。
- Python MVP 仅支持已有镜像或镜像 tar 导入，不做 Python 包构建。

### 2.3 工作量单位

本文工作量使用“人日”估算。

1 人日约等于 1 名开发者 1 个完整工作日的有效开发、联调、基础自测时间，不包含长时间需求变更和大规模返工。

## 3. 优先级定义

### P0：平台地基

必须优先完成。没有 P0，平台无法形成可用闭环。

### P1：制品驱动核心

支撑私有化交付的关键能力。P0 完成后优先做。

### P2：多主机与生产化能力

让平台从单机可用走向多 Docker 主机可用。

### P3：增强能力

提升体验和完整度，但不阻塞首个可用版本。

## 6. 版本节奏建议

### 6.1 MVP 版本

建议周期：6 到 8 周。

包含阶段：

- 阶段 0
- 阶段 1
- 阶段 2 的核心能力

交付目标：

```text
创建项目 -> 创建环境 -> 创建应用 -> 创建服务 -> 填写已有镜像 -> 部署到 Docker 单机 -> 查看状态和日志 -> 修改配置 -> 重新部署 -> 回滚
```

### 6.2 制品驱动可用版

建议周期：10 到 13 周。

包含阶段：

- MVP 版本全部能力
- 阶段 3

交付目标：

```text
上传 Jar/dist/镜像 tar 或从 MinIO 拉取制品 -> 构建或导入镜像 -> 推送已有 registry -> 部署服务 -> 保留制品审计 -> 手动清理制品
```

### 6.3 私有化部署完整可用版

建议周期：16 到 20 周。

包含阶段：

- 制品驱动可用版全部能力
- 阶段 4
- 阶段 5
- 阶段 6 的核心能力

交付目标：

```text
多 Docker 主机 -> 中心 Nginx 网关 -> 域名和证书 -> 分批发布 -> 数据库连接变量注入 -> 基础团队协作
```

## 7. 阶段详细拆解

## 7.1 阶段 0：技术设计与数据模型

周期：1 周  
工作量：5 到 8 人日  
优先级：P0

### 目标

在正式编码前确定平台核心模型和扩展边界，减少后续返工。

### 工作项

| 工作项 | 优先级 | 工作量 |
| --- | --- | --- |
| 梳理 Project / Environment / Application / Service / Release / Artifact 模型 | P0 | 1.5 人日 |
| 设计后端 API 路由、handler、datastore 边界 | P0 | 1.5 人日 |
| 设计 Docker 部署适配器接口 | P0 | 1 人日 |
| 设计前端菜单、页面路由和主流程 | P0 | 1 人日 |
| 设计权限和审计事件清单 | P0 | 1 人日 |
| 输出技术设计文档或接口草案 | P0 | 1 到 2 人日 |

### 验收标准

- 明确核心数据模型。
- 明确哪些字段进入持久化。
- 明确哪些能力复用 Portainer 原有 endpoint、docker、registry、user、team 能力。
- 明确 Docker 单机与未来 Kubernetes 的适配器边界。

周期：3 到 4 周  
工作量：20 到 30 人日  
优先级：P0

### 目标

让用户可以通过应用视角部署一个已有镜像到 Docker 单机，并看到运行状态。

### 工作项

| 工作项 | 优先级 | 工作量 |
| --- | --- | --- |
| 项目管理后端 API | P0 | 2 到 3 人日 |
| 环境管理后端 API | P0 | 2 到 3 人日 |
| 应用管理后端 API | P0 | 2 到 3 人日 |
| 服务管理后端 API | P0 | 3 到 4 人日 |
| 发布记录模型与 API | P0 | 3 到 4 人日 |
| 已有镜像部署到 Docker 单机 | P0 | 4 到 6 人日 |
| 服务状态读取 | P0 | 2 到 3 人日 |
| 服务日志读取 | P0 | 1 到 2 人日 |
| HTTP / TCP 健康检查基础能力 | P0 | 2 到 3 人日 |

| 应用部署向导基础版 | P0 | 4 到 6 人日 |

### 验收标准

- 可以创建项目、环境、应用、服务。
- 可以填写已有镜像地址。

- 可以查看服务运行状态、容器 ID、端口、日志。

- 健康检查失败能显示明确原因。

## 7.3 阶段 2：配置、回滚、权限与审计

周期：2 到 3 周  
工作量：15 到 24 人日  
优先级：P0

### 目标

补齐部署平台的安全能力，避免“能部署但不可控”。

### 工作项

| 工作项 | 优先级 | 工作量 |
| --- | --- | --- |
| 项目级、环境级、服务级配置 | P0 | 3 到 4 人日 |
| 敏感变量加密、脱敏、权限控制 | P0 | 3 到 5 人日 |
| 发布配置快照 | P0 | 2 到 3 人日 |
| 配置变更后提示重新部署 | P0 | 1 到 2 人日 |
| 重新部署 | P0 | 2 到 3 人日 |
| 回滚到历史版本 | P0 | 3 到 5 人日 |
| 基础 RBAC | P0 | 3 到 4 人日 |
| 审计日志基础能力 | P0 | 3 到 5 人日 |

### 验收标准

- 服务发布时能注入环境变量。
- 敏感变量默认脱敏。
- 修改敏感变量有审计记录。
- 配置变更后服务能提示需要重新部署。
- 可以用当前版本重新部署。
- 可以选择历史发布版本回滚。
- 项目管理员、开发者、只读观察者权限有基本区分。
- 发布、回滚、配置修改、服务删除等关键行为有审计。

## 7.4 阶段 3：制品驱动部署

周期：4 到 5 周  
工作量：30 到 45 人日  
优先级：P1

### 目标

让平台从“部署已有镜像”升级为“制品驱动部署”，满足不上传源码的私有化交付方式。

### 工作项

| 工作项 | 优先级 | 工作量 |
| --- | --- | --- |
| 制品模型与制品管理 API | P1 | 3 到 5 人日 |
| 手动上传制品 | P1 | 3 到 5 人日 |
| 制品 hash、大小、类型识别 | P1 | 2 到 3 人日 |
| MinIO 配置与拉取制品 | P1 | 4 到 6 人日 |
| 阿里云 OSS 基础兼容验证 | P3 | 2 到 4 人日 |
| 已有 registry 接入与认证 | P1 | 3 到 5 人日 |
| Java 8 Jar 构建镜像 | P1 | 5 到 7 人日 |
| 前端 dist SPA / MPA 构建镜像 | P1 | 5 到 8 人日 |
| 镜像 tar / OCI archive 导入 | P1 | 4 到 6 人日 |
| 推送标准 tag 到 registry | P1 | 2 到 4 人日 |
| 制品保留与手动清理 | P1 | 2 到 4 人日 |
| 制品管理前端页面 | P1 | 4 到 6 人日 |
| 部署向导接入制品来源 | P1 | 3 到 5 人日 |

### 验收标准

- 可以上传 Jar、dist、镜像 tar。
- 可以从 MinIO 拉取制品。
- 制品有来源、大小、hash、上传人、上传时间记录。
- Java 8 Jar 可以构建成镜像并部署。
- 前端 dist 可以选择 SPA 或 MPA 模式并构建成镜像。
- 镜像 tar 可以导入、重新打 tag、推送 registry。
- 原始制品默认保留。
- 用户可以手动清理制品。
- 清理前能看到关联发布和影响提示。

## 8. 关键依赖关系

### 8.1 强依赖

- 发布记录依赖项目、环境、应用、服务模型。
- 回滚依赖发布记录和镜像版本快照。
- 制品构建依赖 registry 接入。
- Nginx 网关依赖服务端口和部署目标。
- 多主机中心网关依赖 `hostIP:publishedPort` 可从网关节点访问。
- 分批发布依赖多主机部署执行器。

### 8.2 可并行项

- 前端页面框架可以与后端模型并行。
- 审计事件定义可以与配置中心并行。
- MinIO 适配可以与 registry 接入并行。
- Java Jar 构建和前端 dist 构建可以在制品模型稳定后并行。
- Nginx 证书管理可以与域名绑定页面并行。

## 9. 风险点与缓冲建议

| 风险 | 影响 | 建议 |
| --- | --- | --- |
| Portainer 原有模型与新应用模型边界不清 | 返工数据结构和 API | 阶段 0 必须画清楚适配边界 |
| 制品构建失败原因复杂 | 用户难以排查 | 每个构建步骤保存日志和状态 |
| registry TLS / 认证差异 | 镜像推送失败 | 先支持常见用户名密码和跳过证书校验 |
| MinIO 与阿里云 OSS API 差异 | 对象存储兼容不稳定 | MinIO 先交付，OSS 单独验收 |
| Nginx 配置错误 | 网关不可用 | reload 前强制 `nginx -t`，失败保持旧配置 |
| 多主机网络不可达 | 中心网关无法访问业务服务 | 环境配置中增加连通性检测 |
| 原始制品长期保留 | 磁盘占用增长 | 阶段 3 必须提供手动清理和容量统计 |
| 权限后补 | 多人使用风险高 | 基础 RBAC 和审计放在阶段 2 |

## 10. 推荐实施顺序

1. 阶段 0：先设计模型和接口。
2. 阶段 1：做已有镜像部署到 Docker 单机。
3. 阶段 2：补配置、回滚、权限、审计。
4. 阶段 3：做制品管理和构建。
5. 阶段 4：做 Nginx 网关和域名证书。
6. 阶段 5：做多 Docker 主机和分批发布。
7. 阶段 6：做数据库绑定、OSS 兼容和体验增强。
8. 阶段 7：按使用反馈做灰度、ACME、监控、Kubernetes。

## 11. 第一阶段最小交付清单

第一阶段建议严格控制边界，只做以下能力：

- 项目管理。
- 环境管理。
- 应用管理。
- 服务管理。
- 已有镜像部署。
- Docker 单机部署。
- 发布记录。
- 服务状态。
- 服务日志。
- HTTP / TCP 健康检查。
- 基础部署向导。

暂不做：

- Jar 构建。
- 前端 dist 构建。
- S3 / MinIO。
- Nginx 网关。
- 多 Docker 主机。
- 分批发布。
- 灰度发布。

这样可以尽快验证平台核心模型是否成立。一旦“应用视角部署已有镜像”的闭环跑通，后续制品、网关、多主机都是在同一发布模型上扩展，不需要推翻重做。

## 12. 当前建议

当前最建议先进入阶段 0，产出技术设计文档，重点确认：

- 新增数据模型是否存入 Portainer BoltDB。
- 新 API 路由归属。
- 应用模型与现有 endpoint、docker、registry 能力的复用方式。
- Docker 单机部署使用容器还是 Stack 作为第一实现。
- 发布记录、配置快照、回滚数据如何保存。
- 审计日志复用 Portainer 现有审计能力，还是新增平台级审计。

这些问题明确后，再进入阶段 1 编码会更稳。
