# 功能优先级与工作量排期

版本：v1.3
日期：2026-07-11
关联文档：[私有化微服务部署平台产品需求文档](./私有化微服务部署平台产品需求文档.md)

## 1. 排期目标

本文档基于私有化微服务部署平台 PRD，梳理功能优先级、版本范围、开发阶段、工作量估算、关键依赖和阶段验收标准。

本版修正阶段 0 评审中暴露的版本、排期和 Gate 口径问题：

- “版本”表示对用户或评审方承诺的能力范围。
- “阶段”表示内部交付顺序。
- “优先级”表示业务必要性，不再直接等同阶段编号。

## 2. 版本范围基线

| 版本 | 定位 | 包含阶段 | 对外承诺 |
| --- | --- | --- | --- |
| V0.1 技术预览版 | 单机已有镜像部署闭环 | 阶段 0、阶段 1 | 管理员可创建项目/环境/应用/服务，部署已有镜像到 Docker 单机，允许短暂停机但失败必须自动恢复旧容器；不建议生产使用 |
| V0.5 制品驱动版 | 私有化制品交付链路 | 阶段 0 到阶段 3 | 对外承诺上传或拉取 Jar/dist/镜像 tar，构建或导入镜像，推送已有 registry 并部署；阶段 2 安全能力若先实现，默认隐藏或内测，不作为 V0.5 对外承诺 |
| V1.0 MVP | 私有化部署完整可用版 | 阶段 0 到阶段 6 的核心能力 | 支持配置安全、中心 Nginx 网关、多 Docker 主机、分批发布、基础团队权限、结构化审计和人工回滚 |
| V1.x 增强版 | 生产增强和平台扩展 | 阶段 7 及后续 | 灰度、ACME、监控日志体系、Kubernetes 适配等 |

说明：PRD 中的“MVP”统一指 V1.0 MVP；V0.1 只作为技术预览版，不承诺生产级无损切换。

## 3. 排期假设

### 3.1 人员假设

默认按 1 到 2 名主要开发者估算。

如果只有 1 名开发者，周期应按上限估算；如果前后端可并行，部分阶段可压缩 20% 到 30%。所有估算包含开发、联调和基础自测，不包含大规模需求变更、正式验收测试、安全测试和生产环境发布演练。

### 3.2 技术假设

- 基于当前 Portainer.CN 二开仓库继续开发。
- V0.1 只支持 Docker 单机和管理员使用。
- V0.1 无中心 Nginx 网关，允许固定端口替换产生短暂停机，但失败必须自动恢复旧容器。
- V1.0 MVP 支持多 Docker 主机、中心 Nginx 网关和分批发布。
- 后续 Kubernetes 作为下一阶段目标，不进入当前主排期。
- 不集成 Git，不拉取源码。
- 最终运行物统一为镜像。
- 私有镜像仓库只接入已有 registry；V0.1 需要支持私有镜像拉取认证，V0.5 再支持标准 tag 推送。
- 对象存储以 MinIO / S3 兼容接口为 V0.5 Gate；阿里云 OSS 做兼容验证，不作为 V0.5 阻断，独立 OSS 适配器进入 V1.0 增强范围。
- Python MVP 仅支持已有镜像或镜像 tar 导入，不做 Python 包构建。

## 7. 阶段 0：评审基线补齐

### 7.1 目标

在正式编码前关闭阶段 0 Gate Review 阻断项，减少发布执行器、数据模型和前端主流程返工。

### 7.2 工作项

| 工作项 | 优先级 | 工作量 |
| --- | --- | --- |
| 统一版本范围、里程碑和需求追踪矩阵 | P0 | 0.5 到 1 人日 |
| 冻结 ServiceDefinition / ServiceDeployment 关系和 ER 图 | P0 | 1 到 1.5 人日 |
| 补完整数据字典、生命周期和归档/删除规则 | P0 | 1 到 1.5 人日 |
| 设计发布状态机、锁、幂等、异步任务、租约续期、超时、取消和重启恢复 | P0 | 1.5 到 2.5 人日 |
| 设计失败补偿矩阵、版本化容器命名和 Docker/Agent candidate 技术 Spike | P0 | 1.5 到 2 人日 |
| 设计前端菜单、路由、部署向导和页面状态 | P0 | 1 到 1.5 人日 |
| 设计 API 契约、嵌套 DTO 数据字典、错误 reason、分页、乐观锁和并发规则 | P0 | 1.5 到 2 人日 |
| 设计权限矩阵和平台审计数据模型 | P0 | 1 到 1.5 人日 |
| 输出阶段 1 验收用例和非功能约束 | P0 | 1 到 1.5 人日 |

### 7.3 验收标准

- PRD、排期和技术设计中的 V0.1 / V0.5 / V1.0 口径一致。
- 明确核心数据模型、持久化字段和生命周期规则。
- 明确 Docker 单机与未来 Kubernetes 的适配器边界。
- 明确 V0.1 发布安全承诺：允许短暂停机但失败自动恢复旧容器。
- 明确发布状态机、异步协议、锁、幂等、租约续期、超时、取消和重启恢复。
- 明确前端菜单、路由、主流程、页面状态和角色可见性。
- 明确权限矩阵和结构化平台审计 schema。
- 明确阶段 1 可测试验收用例。`ServiceDeployment.SpecRevision`、`CurrentServingReleaseID`、`LastDeployedSpecRevision`、嵌套 DTO、错误 reason、queued watchdog 和任务执行策略不得再留给编码阶段猜测。

## 8. 阶段 1：V0.1 技术预览闭环

### 8.1 目标

让管理员可以通过应用视角部署一个已有镜像到 Docker 单机，并看到运行状态。V0.1 不承诺生产级无损切换，允许短暂停机，但发布失败必须自动尝试恢复旧容器并留下可诊断记录。

### 8.2 工作项

| 工作项 | 优先级 | 工作量 |
| --- | --- | --- |
| Project / Environment 后端 API | P0 | 4 到 6 人日 |
| Application / ServiceDefinition / ServiceDeployment 后端 API | P0 | 5 到 7 人日 |
| Artifact image-reference 模型与 API | P0 | 2 到 3 人日 |
| 私有 registry 拉取认证复用 | P0 | 2 到 3 人日 |
| Release 模型、状态机、异步 API | P0 | 4 到 6 人日 |
| 发布互斥、幂等键、超时和重启恢复 | P0 | 3 到 5 人日 |
| Docker 单机 ContainerAdapter | P0 | 5 到 7 人日 |
| 自动恢复旧容器和孤儿资源清理 | P0 | 3 到 5 人日 |
| 服务状态、日志、运行资源丢失提示 | P0 | 2 到 3 人日 |
| HTTP / TCP 健康检查基础能力 | P0 | 2 到 3 人日 |
| 管理员权限与最小平台审计落库 | P0 | 2 到 3 人日 |
| 项目、环境、应用、服务前端页面 | P0 | 5 到 7 人日 |
| 应用部署向导基础版 | P0 | 4 到 6 人日 |

### 8.3 验收标准

- 管理员可以创建项目、环境、应用、逻辑服务和环境部署配置。
- 管理员可以填写已有镜像地址，并使用 Portainer registry 凭据拉取私有镜像。
- 管理员可以选择 Docker 单机作为部署目标。
- 发布请求返回 releaseId，前端能查看发布中、成功、失败、恢复中、恢复失败状态。
- 同一服务环境同时只能有一个进行中发布；重复提交按幂等键返回同一 release。
- 镜像拉取失败、端口冲突、健康检查失败都有明确错误码和页面提示。
- 替换失败时系统自动尝试恢复旧容器；恢复失败时标记“需人工处置”。
- 服务详情能展示运行状态、容器 ID、端口、日志和发布记录。
- 外部删除容器后，服务详情显示运行资源丢失，不把 Service 配置误标为删除。
- V0.1 UI 明确提示该版本不建议用于生产无损发布。

## 9. 阶段 2 到阶段 7 摘要

阶段 2 到阶段 6 的工作量在本轮保持 ROM 粗估：只用于版本规划和资源预估，不作为进入开发的详细排期。每个阶段启动前需要按阶段 1 的粒度重新拆工作包、验收用例和风险项。

### 9.1 阶段 2：配置、人工回滚、权限与审计

目标：补齐 V1.0 所需安全能力。人工选择历史版本回滚从阶段 2 开始开放；阶段 1 只做失败自动恢复旧容器。

核心验收：三级配置、敏感变量、配置快照、配置漂移、项目角色、结构化审计、人工回滚。

### 9.2 阶段 3：V0.5 制品驱动部署

目标：让平台从“部署已有镜像”升级为“制品驱动部署”。

核心验收：上传 Jar/dist/镜像 tar，从 MinIO 拉取制品，构建或导入镜像，推送标准 tag，保留和清理原始制品。

### 9.3 阶段 4：Nginx 网关与域名证书

目标：让 HTTP 服务通过统一域名和路径访问，并在网关切流下满足“发布失败不影响当前线上版本”。

核心验收：Nginx 配置生成、`nginx -t`、reload 失败保持旧配置、域名绑定、路径转发、手动证书。

### 9.4 阶段 5：多 Docker 主机与分批发布

目标：让平台支持多台 Docker 主机，并通过中心 Nginx 网关转发到不同主机上的服务。

核心验收：环境绑定多台主机、主机组、分批发布、失败暂停、每台主机结果可追踪。

### 9.5 阶段 6：数据库绑定与兼容增强

目标：增强平台日常可用性，并打通数据库工作台和应用部署之间的关系。

核心验收：服务绑定数据库连接、生成数据库变量、从服务页进入数据库工作台、OSS 兼容增强、容量提醒和失败诊断优化。

### 9.6 阶段 7：增强能力

目标：按使用反馈补充灰度、ACME、监控、日志和 Kubernetes。

## 10. 关键依赖关系

| 依赖 | 说明 |
| --- | --- |
| 发布记录依赖核心模型 | Release 必须引用 Project、Environment、Application、ServiceDeployment、Artifact |
| 人工回滚依赖不可变快照 | 阶段 2 开放人工回滚前，阶段 1 必须保存 digest、配置快照和目标快照 |
| 制品构建依赖 registry 推送 | 阶段 1 只需 registry 拉取认证，阶段 3 才要求标准 tag 推送 |
| 网关依赖服务端口和部署目标 | 阶段 4 的切流需要阶段 1 的端口、健康检查和运行引用稳定 |
| 多主机中心网关依赖可达 HostAddress | 阶段 5 必须验证网关节点可以访问业务主机发布端口 |
| 分批发布依赖多目标执行器 | 阶段 5 才扩展 Release.TargetResults 为多主机批次结果 |

## 11. 风险点与缓冲建议

| 风险 | 影响 | 建议 |
| --- | --- | --- |
| V0.1 被误用于生产无损发布 | 用户预期错误 | UI 和文档明确“不建议生产使用”，生产环境部署二次确认 |
| Portainer 原有模型与新应用模型边界不清 | 数据结构返工 | 阶段 0 固定 ServiceDefinition / ServiceDeployment |
| Docker fixed port 替换失败 | 短暂停机或需人工处置 | 阶段 1 必须使用版本化容器名、保留旧容器 RuntimeRef 并实现恢复矩阵 |
| 可变 tag 导致回滚不可复现 | 回滚失败或部署内容漂移 | 发布时解析 digest，失败时标记弱可追溯 |
| registry TLS / 认证差异 | 镜像拉取或推送失败 | 阶段 1 支持常见拉取认证和跳过证书校验，阶段 3 扩展推送 |
| MinIO 与阿里云 OSS API 差异 | 对象存储兼容不稳定 | MinIO / S3 兼容接口先交付；阿里云 OSS 做兼容验证，独立适配器单独验收 |
| Nginx 配置错误 | 网关不可用 | reload 前强制 `nginx -t`，失败保持旧配置 |
| 多主机网络不可达 | 中心网关无法访问业务服务 | 环境配置中增加连通性检测 |
| 权限后补 | 多人使用风险高 | V0.1 限管理员；V1.0 前补齐 RBAC 和结构化审计 |

## 12. 阶段 1 测试策略摘要

阶段 1 至少覆盖以下验收用例：

- 正常创建项目、环境、应用、逻辑服务和环境部署配置。
- 公开镜像发布成功。
- 私有镜像凭据正确发布成功。
- 私有镜像凭据错误，发布校验失败。
- 端口冲突，发布校验失败，错误 reason 为 `PORT_CONFLICT`。
- 镜像拉取失败，发布失败且不影响旧容器，Release step reason 为 `IMAGE_PULL_FAILED`。
- candidate 健康检查失败，candidate 被清理，旧容器保持运行，错误 reason 为 `HEALTHCHECK_FAILED` 或 `HEALTHCHECK_HOST_UNREACHABLE`。
- 正式容器启动失败，自动恢复旧容器。
- 旧容器恢复失败，标记“需人工处置”。
- 重复点击发布按钮，返回同一 release。
- 同一服务环境并发发布被拒绝。
- Portainer 进程重启后 stuck release 被标记 interrupted，candidate 孤儿容器可清理。
- 外部删除容器后，服务详情显示运行资源丢失。
- 非管理员访问 `/api/platform` 业务接口被拒绝；发布相关拒绝写入最小平台审计，非发布类 denied 审计不作为 V0.1 Gate。

## 13. 当前建议

阶段 0 先完成 Gate 0A 文档与模型冻结，再进入阶段 1 的模型、CRUD、异步框架和前端骨架；Docker 发布执行器必须等待 Gate 0B Docker/Agent Spike 通过。发布状态机、API 契约、模型生命周期和失败补偿矩阵必须作为编码前置输入。
