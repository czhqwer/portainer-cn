## 1. 使用方式

在 Codex 中创建 Goal 时，复制“总控 Goal 提示词”。如果中途被中断或需要重新唤起同一个 Goal，复制“续跑提示词”。

本模板用于让 Codex 按阶段 1 分批实施方案自动推进：每一批必须实现、验证、提交后，才能进入下一批。Goal 完成条件是阶段 1 全部批次有当前工作区证据证明已经完成。

## 2. 总控 Goal 提示词

```text
目标：根据 docs/阶段1分批实施方案.md，按批次 1 到批次 7 顺序完成阶段 1 开发。每一批必须实现、测试通过、提交对应代码后，才能进入下一批。

工作方式：

1. 先读取并遵守以下文档：
   - AGENTS.md
   - docs/阶段1分批实施方案.md
   - docs/需求评审结论.md
   - docs/阶段0平台核心模型与后端边界设计.md
   - docs/私有化微服务部署平台产品需求文档.md
   - docs/功能优先级与工作量排期.md

2. 先检查当前状态：
   - 执行 git status --short --branch。
   - 查看最近提交和现有 docs/阶段1分批实施方案.md。
   - 判断当前应从哪个批次继续：不要重复已经有提交和测试证据证明完成的批次；如果证据不足，先补验证或补缺口。

3. 按批次顺序推进：
   - 批次 1：文档基线与 CR 收口。
   - 批次 2：后端核心模型与 dataservice。
   - 批次 3：平台 CRUD API 与管理员权限。
   - 批次 4：Artifact 与 Release 控制平面。
   - 批次 5：前端页面骨架与部署向导。
   - 批次 6：Gate 0B Spike 与 Docker 执行器。
   - 批次 7：运行状态、日志、恢复与阶段 1 验收。

4. 每批开始前必须做批次审计：
   - 从 docs/阶段1分批实施方案.md 提取本批目标、范围、不做项、依赖、交付物、验收标准。
   - 搜索当前代码和文档，确认本批缺口。
   - 制定本批实现计划并用 update_plan 跟踪。

5. 每批实现规则：
   - 严格遵守 Gate 边界。Gate 0B 通过前，只能做批次 1 到批次 5，不得实现 Docker 发布执行器正式代码，不得创建真实 candidate 容器，不得停止正式容器，不得执行端口切换。
   - 批次 6 必须先完成 Docker/Agent candidate Spike 并把结论回填 docs；只有 Spike 结论证明 Gate 0B 通过后，才能实现 RuntimeDriver / ContainerAdapter / SingleTargetExecutor。
   - V0.1 所有 /api/platform 业务接口包括读取都限制管理员访问。
   - 部署输入只能是制品或镜像，不引入 Git、源码构建、内置 registry、Kubernetes 部署、多主机、中心 Nginx 网关、完整 RBAC、人工历史版本回滚。
   - 优先沿用仓库已有结构、组件、handler、dataservice、错误处理、i18n 和测试风格。
   - 不回滚用户或其他协作者已有改动；只提交本批相关文件。

6. 每批验证规则：
   - 后端模型、dataservice、handler 或状态机改动后，运行相关 go test。
   - 前端 TypeScript 改动后，运行 pnpm typecheck。
   - 文档批次至少检查关键旧口径是否清除、链接是否正确、git diff 是否符合批次范围。
   - 如果测试失败，先修复并重跑；不得在测试失败时提交，除非失败明确与本批无关并在最终说明中给出证据。

7. 每批提交规则：
   - 每批完成并验证后，执行 git status --short，确认只包含本批相关改动。
   - stage 本批相关文件。
   - 使用中文 commit message，格式建议：
     - 批次 1：docs: 固化阶段1分批实施方案
     - 批次 2：feat: 新增平台核心模型与数据服务
     - 批次 3：feat: 新增平台 CRUD API 与管理员权限
     - 批次 4：feat: 新增制品与发布控制平面
     - 批次 5：feat: 新增阶段1前端页面骨架
     - 批次 6：feat: 接入 Docker 单机发布执行器
     - 批次 7：feat: 补齐运行状态恢复与阶段1验收
   - 提交成功后，在回复中说明本批提交哈希、验证命令和结果，再继续下一批。

8. 进度记录：
   - 维护或创建 docs/阶段1实施进度.md。
   - 每批提交后记录：批次、提交哈希、完成内容、验证命令、测试结果、遗留风险、是否允许进入下一批。

9. 完成判定：
   - 只有当批次 1 到批次 7 都有提交、验证结果和当前状态证据证明完成后，才能把 Goal 标记为 complete。
   - 如果遇到 Gate 0B 未通过、测试环境缺失或需要用户提供外部环境，先尽量完成可本地推进的验证和文档记录；只有同一阻塞条件连续三轮仍无法推进时，才按 Goal 模式 blocked 规则处理。

从现在开始执行：先审计当前仓库状态，判断应该从第几批继续，然后按上述规则推进。
```

## 3. 续跑提示词

```text
继续当前阶段 1 Goal。

请先读取：
- docs/阶段1分批实施方案.md
- docs/阶段1实施进度.md（如果存在）
- git log --oneline -n 20
- git status --short --branch

然后判断下一步：
1. 如果上一批已经提交且测试证据充分，进入下一批。
2. 如果上一批有提交但测试证据不足，先补验证；必要时补修复提交。
3. 如果上一批未提交，继续完成该批，实现、测试、提交后再进入下一批。
4. 如果已经进入批次 6，但 Gate 0B Spike 结论缺失，先完成 Spike 和 docs 回填，不得提前实现 Docker 发布执行器。

仍然必须遵守：
- 每批实现、测试通过、中文 commit 后再进入下一批。
- 不提交无关文件。
- 不回滚用户改动。
- V0.1 /api/platform 全业务接口仅管理员访问。
- Gate 0B 前不得实现真实 Docker 执行链路。
```

## 4. 批次完成审计清单

每一批提交前，Codex 必须逐项确认：

- 本批 `目标 / 范围 / 不做 / 依赖 / 交付物 / 验收标准` 已从 `docs/阶段1分批实施方案.md` 对齐。
- 当前改动没有越过本批边界。
- 相关测试或检查已经运行。
- `git status --short` 只包含本批相关文件。
- commit message 使用中文。
- `docs/阶段1实施进度.md` 已记录本批提交和验证结果。

## 5. Gate 0B 红线提示

批次 6 前必须再次确认：

- Spike 覆盖容器化 Portainer + Docker socket、本地 Agent、远程 Agent、candidate 随机端口探测、版本化容器命名、candidate 验证后停止/删除、正式端口切换、旧容器恢复与私有镜像认证。
- Spike 结论已回填到 docs。
- Spike 明确给出默认策略、失败 reason 和不可自动推断时的用户配置路径。

未满足以上条件时，Codex 只能继续补 Spike 和文档，不得实现 Docker 发布执行器正式代码。
