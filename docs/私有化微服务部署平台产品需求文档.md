# 私有化微服务部署平台 PRD

版本：v1.3
日期：2026-07-11
基础项目：Portainer Community Edition 二次开发

## 1. 背景与定位

本项目基于 Portainer Community Edition 二次开发，目标是从“容器管理面板”升级为“制品驱动的私有化微服务交付平台”。

平台不集成 Git，不在客户环境保存源码。用户以镜像、镜像 tar、Java Jar、前端 dist 包等制品作为输入，平台负责制品校验、镜像构建或导入、推送已有私有镜像仓库、部署到 Docker 主机、配置网关、记录发布历史并支持回滚。

产品目标覆盖 Docker 单机和多台 Docker 主机。交付上先提供 Docker 单机技术预览版，用于验证应用模型和发布闭环；V1.0 MVP 再包含中心 Nginx 网关、多 Docker 主机、分批发布、基础团队权限和结构化审计。后续扩展 Kubernetes。

## 2. 产品目标

### 2.1 核心目标

- 建立项目、环境、应用、服务的统一应用模型。
- 提供统一的“应用部署”入口，弱化 Stack、Container、Kubernetes YAML 等底层概念。
- 支持部署已有镜像。
- 支持从手动上传或对象存储拉取制品，并包装为运行镜像。
- 支持 Java 8 Jar、前端 dist、Docker 镜像 tar 等核心制品。
- 支持接入已有私有镜像仓库。
- 支持 MinIO / S3 兼容对象存储；阿里云 OSS 做兼容验证，独立适配器不作为 V0.5 Gate。
- 支持配置中心、敏感变量、域名、网关、证书、发布记录、回滚、日志、监控、健康检查。
- 支持管理员、项目管理员、开发者、只读观察者的权限边界。
- 支持关键操作审计。

### 2.2 非目标

V1.0 MVP 阶段不做以下能力：

- Git 集成。
- 源码构建。
- 平台内置私有镜像仓库。
- 数据库实例创建、备份、恢复。
- Kubernetes 部署。
- 完整 CI/CD 流水线。
- 复杂审批流。
- 多租户计费。
- 制品漏洞扫描。
- Python 源码包构建。

### 2.3 版本范围基线

为避免“MVP”和“阶段”混用，后续文档统一按版本承诺能力，按阶段安排交付顺序。

| 版本 | 定位 | 必须包含 | 明确不包含 |
| --- | --- | --- | --- |
| V0.1 技术预览版 | 验证应用模型和 Docker 单机已有镜像发布闭环 | 项目、环境、应用、逻辑服务、环境部署配置、已有镜像制品、Docker 单机发布、发布记录、状态和日志、管理员使用、私有镜像拉取认证、失败后自动恢复旧容器 | 制品构建、MinIO、中心 Nginx 网关、多主机、分批发布、完整 RBAC、人工历史版本回滚、生产级无损切换 |
| V0.5 制品驱动版 | 验证私有化制品交付链路 | V0.1 能力、Jar/dist/镜像 tar、MinIO 拉取、制品保留和清理、标准 tag、推送已有 registry | 多主机生产发布、完整团队权限、复杂灰度 |
| V1.0 MVP | 面向私有化部署的完整可用版本 | V0.5 能力、配置中心、敏感变量、中心 Nginx 网关、域名和证书、多 Docker 主机、分批发布、基础 RBAC、结构化审计、人工回滚 | Git、源码构建、内置 registry、Kubernetes、完整 CI/CD、复杂审批 |
| V1.x 增强版 | 生产增强和平台扩展 | HTTP 灰度、ACME、Prometheus/Loki/Grafana、Kubernetes 适配 | 按后续需求确认 |

## 3. 核心原则

- 私有化交付优先，不要求客户环境存在业务源码。
- 所有部署输入都必须是制品，不是源码仓库。
- 构建过程只做“制品包装”，不做源码编译。
- 最终运行物统一为镜像。
- 平台只接入已有 registry，不内置 registry。
- 日常用户从应用视角操作，底层 Portainer 能力保留在高级管理中。
- V1.0 MVP 及之后的网关发布必须满足“发布失败不能影响当前线上版本”；V0.1 技术预览版在无网关、固定宿主机端口的限制下，允许短暂停机，但必须保留旧容器信息并在失败时自动恢复旧容器，同时在页面明确标注“不建议生产使用”。
- 敏感配置必须加密、脱敏、可审计。
- Docker 与未来 Kubernetes 部署逻辑通过适配器隔离。

### 4.1 管理员

能力包括：

- 创建应用和服务。

## 5. 核心领域模型

### 5.1 项目 Project

项目是最高业务组织单元。

示例：

- 商城系统
- 内部工具平台
- 客户私有化项目

项目包含：

- 项目名称
- 项目标识
- 描述
- 成员
- 环境
- 应用
- 项目级配置
- 审计日志

### 5.2 环境 Environment

环境表示项目的部署阶段。

默认支持：

- dev
- test
- prod

环境包含：

- 环境名称
- 环境标识
- 部署目标
- 环境级配置
- 网关策略
- 发布策略

### 5.3 应用 Application

应用是项目下的可部署业务单元。

示例：

- 用户中心
- 订单系统
- 管理后台
- 数据同步任务

应用包含：

- 应用名称
- 应用标识
- 所属项目
- 服务列表
- 应用级概览

### 5.4 服务 Service

服务是实际部署和运行的最小业务单元。产品语义上服务拆为两层：

- `ServiceDefinition`：逻辑服务，属于应用，跨环境复用，例如“订单 API”。
- `ServiceDeployment`：服务在某个环境中的部署配置和运行事实，例如“订单 API / prod”。

用户创建一次逻辑服务，再为 dev/test/prod 等环境维护不同的部署配置。发布记录挂在 `ServiceDeployment` 下。

服务类型包括：

- frontend
- backend
- worker
- scheduler
- java-service
- static-site
- python-service
- python-job
- database
- redis

MVP 中 database 和 redis 主要作为连接绑定和展示对象，不负责创建数据库或中间件实例。

逻辑服务包含：

- 服务名称
- 服务标识
- 服务类型
- 所属项目
- 所属应用

环境部署配置包含：

- 所属环境
- 制品来源
- 镜像配置
- 端口配置
- 域名配置
- 环境变量
- 敏感变量
- 挂载卷
- 健康检查
- 部署目标
- 副本数
- 发布策略
- 当前运行版本
- 期望配置版本
- 最近成功发布
- 配置漂移状态

制品是平台部署的输入。

支持类型：

## 6. 部署目标

### 6.1 Docker 单机

V0.1 技术预览版优先支持。

能力包括：

- 在当前 Docker 环境创建容器。
- 绑定端口。
- 配置环境变量。
- 配置卷。
- 查看容器日志和状态。

V0.1 不引入中心 Nginx 网关，因此固定宿主机端口替换期间可能产生短暂停机。该版本的验收目标是：

- 发布前尽量通过临时端口或可达地址执行 candidate 健康检查。
- 运行容器采用版本化命名，平台通过 `CurrentServingReleaseID` 和 `RuntimeRef` 找到当前容器，不依赖固定容器名。
- 停止旧容器前保存旧容器引用和配置快照。
- 新容器启动或健康检查失败时自动恢复旧容器。
- 失败恢复失败时明确标记人工处置状态，并保留诊断信息。
- UI 在生产环境部署前提示该版本不承诺无损切换。

### 6.2 多 Docker 主机

V1.0 MVP 支持多台 Docker 主机。

策略：

- 每个环境可以绑定一个或多个 Docker 主机。
- 服务发布时选择目标主机或主机组。
- HTTP 服务通过中心 Nginx 网关暴露。
- worker、scheduler、python-job 等非 HTTP 服务按主机分批发布。

### 6.3 Kubernetes

后续阶段支持。

映射关系：

- Project / Environment -> Namespace / Label
- Service -> Deployment / CronJob
- Config -> ConfigMap
- Secret -> Secret
- Domain Route -> Ingress
- Health Check -> Probe
- Release -> Deployment revision

## 7. 制品来源

### 7.1 已有镜像

用户直接填写镜像地址。

示例：

```text
registry.example.com/mall/order-api:1.0.0
harbor.example.com/project/admin-web:20260709
```

平台校验：

- 镜像地址格式。
- 当前 Docker 主机是否可拉取。
- registry 认证是否可用。
- 镜像元信息是否可读取。

校验通过后直接部署。

### 7.2 手动上传

用户在平台上传制品。

支持：

- `.jar`
- `.zip`
- `.tar`
- `.tar.gz`
- Docker image tar
- OCI archive

上传后平台需要：

- 限制最大文件大小。
- 计算 SHA256。
- 判断制品类型。
- 保存制品元数据。
- 保存原始制品用于审计和重新构建。
- 支持用户手动清理原始制品。

### 7.3 S3 / MinIO / 阿里云 OSS

对象存储主要目标为 MinIO / S3 兼容接口；阿里云 OSS 做兼容验证，不作为 V0.5 Gate。

V0.5 制品驱动版建议实现：

- S3 兼容协议适配 MinIO。
- 阿里云 OSS 在 V0.5 仅做兼容验证；若目标环境不能通过 S3 兼容 endpoint 接入，独立 OSS 适配器进入 V1.0 增强范围。

对象存储配置项：

- 存储类型：MinIO / S3 Compatible / Aliyun OSS
- endpoint
- region
- bucket
- access key
- secret key
- path prefix
- 是否启用 TLS
- 是否跳过证书校验
- 默认下载超时
- 最大文件大小

部署时用户可以：

- 浏览对象路径，后续可选。
- 手动输入对象路径。
- 拉取制品到平台。
- 校验 SHA256，若用户提供期望 hash。
- 进入构建或导入流程。

## 8. 构建与镜像管理

### 8.1 构建定位

平台构建不是源码构建，而是制品包装。

统一流程：

1. 获取制品。
2. 校验类型、大小、hash。
3. 选择构建模板。
4. 构建运行镜像或导入镜像。
5. 打平台标准 tag。
6. 推送已有私有 registry。
7. 使用最终镜像部署。
8. 保存发布记录。

### 8.2 私有 registry

平台只接入已有 registry。

配置项：

- registry 地址
- 用户名
- 密码或 token
- 是否启用 TLS
- 是否跳过证书校验
- 默认命名空间

建议镜像 tag 规则：

```text
{registry}/{project}/{environment}/{application}-{service}:{version}
```

示例：

```text
registry.local/mall/prod/order-api:20260709-153012
```

### 8.3 Java Jar 构建

V0.5 制品驱动版优先支持 Java 8。

用户配置：

- Java 版本：默认 Java 8
- Jar 文件
- 启动参数
- JVM 参数
- 服务端口
- 健康检查路径
- 工作目录
- 环境变量

平台行为：

- 使用受控 Java 8 基础镜像。
- 将 Jar 包复制到固定工作目录。
- 生成标准启动命令。
- 构建镜像并推送 registry。
- 部署生成镜像。

### 8.4 前端 dist 构建

支持上传或从对象存储拉取前端 dist 压缩包。

前端 dist 运行模式：

- SPA：单页应用，刷新任意前端路由回退到 `index.html`。
- MPA / 纯静态站点：多页面或普通静态站点，路径按真实文件解析，不做统一 fallback。
- 静态资源包：只作为资源目录被其他服务引用，MVP 不作为独立部署类型优先实现。
- SSR / Node 前端服务：不按 dist 构建处理，MVP 要求用户提供已有镜像。

V0.5 制品驱动版支持：

- SPA
- MPA / 纯静态站点

用户配置：

- 运行模式：SPA / MPA
- 默认首页
- 服务端口
- 是否启用 gzip
- 静态资源缓存策略
- 404 页面，后续可选

平台行为：

- 解压 dist。
- 校验入口文件。
- 使用受控 Nginx 静态镜像。
- 生成站点 Nginx 配置。
- 构建镜像并推送 registry。
- 部署生成镜像。

### 8.5 镜像 tar 导入

支持 Docker image tar 和 OCI archive。

平台行为：

1. 导入镜像。
2. 读取镜像元信息。
3. 展示原始镜像名称、tag、架构、创建时间。
4. 重新打平台标准 tag。
5. 推送已有 registry。
6. 部署标准 tag。

### 8.6 Python 服务

V1.0 MVP 阶段 Python 仅支持已有镜像部署。

适用场景：

- FastAPI Web 服务。
- 定时任务。
- 脚本任务。

用户需要自行准备镜像并推送到 registry，或上传镜像 tar 后由平台导入。

后续可扩展：

- pex
- pyz
- wheel
- 混淆后的 Python 包

## 9. 应用部署入口

### 9.1 入口目标

用户不需要直接从 Stack、Container 或 YAML 开始。

部署入口以应用视角组织：

1. 选择项目。
2. 选择环境。
3. 选择应用。
4. 选择或创建服务。
5. 选择服务类型。
6. 选择制品来源。
7. 配置端口、域名、环境变量、数据库连接。
8. 执行校验。
9. 提交异步发布任务。

### 9.2 服务类型

V0.1 技术预览版仅开放适合固定端口替换和 candidate 验证的长运行服务类型：

| 服务类型 | V0.1 是否开放 | 说明 |
| --- | --- | --- |
| frontend / static-site | 开放 | 仅限已有镜像部署，支持 HTTP/TCP/startup-only 验证 |
| backend | 开放 | 仅限已有镜像部署，建议配置 HTTP/TCP 健康验证 |
| python-service | 条件开放 | 仅限已有镜像且为长运行 HTTP/TCP 服务 |
| java-service | 条件开放 | V0.1 仅支持已有镜像；Jar 构建进入 V0.5 |
| worker / scheduler / python-job | 隐藏 | candidate 启动可能重复消费任务，V0.1 不开放 |
| database / redis | 隐藏 | MVP 中仅作为绑定和展示对象，不创建实例 |

V1.0 MVP 支持：

- Java 后端
- 前端静态站点
- 已有镜像服务
- Worker
- Scheduler
- Python 镜像服务
- Python 镜像任务

后续支持：

- Go 后端模板
- Node.js 后端模板
- 更多语言运行模板

由于不集成 Git 且不保存源码，Go、Node.js 等服务在 MVP 中建议优先通过已有镜像或镜像 tar 部署。

### 9.3 部署前校验

部署前必须校验：

- 项目、环境、应用、服务是否完整。
- 制品是否可用。
- 制品 hash 是否一致。
- registry 是否可推送。
- Docker 主机是否在线。
- 镜像是否可拉取。
- 镜像 digest 是否可解析；无法解析时必须标记为弱可追溯发布，并限制回滚承诺。
- 端口是否冲突。
- 域名路由是否冲突。
- 健康检查配置是否合理。
- 敏感变量是否完整。
- 数据库连接是否可用，若服务依赖数据库。

## 10. 配置中心

### 10.1 配置层级

支持三级配置：

- 项目级配置
- 环境级配置
- 服务级配置

优先级：

```text
服务级 > 环境级 > 项目级
```

### 10.2 配置类型

- 普通环境变量
- 敏感环境变量
- 引用变量
- 数据库连接变量
- Redis 连接变量

### 10.3 敏感变量

要求：

- 加密保存。
- 页面默认脱敏。
- 复制和查看明文需要权限。
- 修改后记录审计。
- 发布时注入容器环境变量。
- 不在日志和审计详情中明文展示。

### 10.4 配置变更提示

服务运行后，如果配置发生变化，应提示：

```text
配置已变更，当前运行实例尚未重新部署。
```

用户可以：

- 查看配置差异。
- 立即重新部署。
- 稍后处理。

## 11. 数据库连接

## 12. 网关、域名与证书

### 12.1 内置 Nginx 的目的

内置 Nginx 的目标是提供统一入口，而不是替代业务服务。

它解决：

- 统一域名访问入口。
- 自动反向代理到 Docker 服务。
- HTTPS 证书挂载和切换。
- 路径转发，例如 `/api` 到后端，`/` 到前端。
- 避免用户直接暴露大量容器端口。
- 为灰度或分批发布提供流量控制基础。
- 多 Docker 主机场景中提供中心入口。

### 12.2 Docker 单机场景

平台部署一个受控 Nginx 容器。

发布 HTTP 服务后：

- 自动生成 upstream。
- 自动生成 server 和 location。
- 校验 Nginx 配置。
- reload Nginx。
- reload 失败则保持旧配置。

### 12.3 多 Docker 主机场景

V1.0 MVP 接受中心 Nginx 网关模式。

模式：

- 指定一台 Docker 主机作为网关节点。
- Nginx 部署在网关节点。
- 业务服务部署在一台或多台 Docker 主机。
- Nginx 通过 `hostIP:publishedPort` 转发到业务服务。

后续可扩展：

- 每台主机边缘 Nginx。
- Keepalived 高可用入口。
- Kubernetes Ingress。

### 12.4 域名与路由

每个 HTTP 服务支持：

- 域名。
- 路径前缀。
- 目标端口。
- HTTPS 开关。
- 强制 HTTPS。
- WebSocket 支持。
- 代理超时。
- 最大上传大小。

示例：

```text
admin.example.com/      -> frontend:80
api.example.com/        -> backend:8080
example.com/api         -> backend:8080
example.com/            -> frontend:80
```

### 12.5 证书管理

V1.0 MVP 支持：

- 手动上传证书。
- 选择已有证书。
- 服务绑定证书。

后续支持：

- ACME 自动签发。
- 证书过期提醒。

## 13. 发布管理

### 13.1 发布状态

发布状态包括：

- 待校验
- 校验中
- 构建中
- 推送中
- 部署中
- 恢复中
- 健康检查中
- 成功
- 失败
- 恢复失败，需人工处置
- 已回滚
- 已取消

发布任务采用异步执行。创建发布请求返回发布 ID，前端通过发布详情或事件轮询查看状态；同一服务环境同一时间只允许一个进行中的发布。

### 13.2 标准发布流程

1. 选择项目、环境、应用、服务。
2. 选择制品来源。
3. 填写版本号。
4. 配置端口、环境变量、域名、健康检查。
5. 执行部署前校验。
6. 构建或导入镜像。
7. 推送 registry。
8. 在目标 Docker 主机部署。
9. V0.1 单机技术预览版执行固定端口替换，允许短暂停机，失败时自动恢复旧容器。
10. V1.0 MVP 更新 Nginx 网关并切流，网关 reload 失败保持旧配置。
11. 执行健康检查。
12. 保存发布记录。

### 13.3 重新部署

使用当前版本重新部署。

适用场景：

- 配置已变更。
- 容器异常。
- 主机迁移。
- 手动恢复。

### 13.4 回滚

用户选择历史发布版本回滚。

流程：

1. 校验历史镜像是否仍存在。
2. 展示版本差异和配置差异。
3. 用户二次确认。
4. 部署历史镜像。
5. 更新网关。
6. 执行健康检查。
7. 记录回滚发布。

### 13.5 分批发布

MVP 优先支持分批发布。

适用：

- HTTP 服务。
- worker。
- scheduler。
- python-job。

配置项：

- 每批主机数量。
- 每批间隔。
- 失败是否暂停。
- 健康检查失败是否回滚。

### 13.6 灰度发布

V1.0 MVP 暂缓复杂灰度，多主机先使用分批发布；复杂 HTTP 灰度作为后续增强。

后续 HTTP 服务支持基于 Nginx upstream 权重的灰度发布：

```text
v1: 90%
v2: 10%
```

能力包括：

- 创建灰度版本。
- 设置流量比例。
- 扩大比例。
- 全量切换。
- 取消灰度。
- 灰度失败回滚。

非 HTTP 服务不做流量灰度，只做分批发布。

## 15. 健康检查

支持类型：

- HTTP GET。
- TCP 端口探测。
- 命令探测，后续可选。

配置项：

- 检查路径。
- 检查间隔。
- 超时时间。
- 成功阈值。
- 失败阈值。
- 首次启动宽限时间。

发布后必须记录健康验证结果。健康验证分为三档：

| 等级 | 说明 | 适用范围 |
| --- | --- | --- |
| `verified` | HTTP/TCP 健康检查通过 | 推荐所有 HTTP/TCP 服务使用，生产环境默认要求 |
| `startup-only` | 仅确认容器在启动宽限期内持续运行 | 仅 V0.1 非生产环境可用，页面必须提示未验证业务健康 |
| `unverified` | 没有可用验证，只能记录容器启动尝试 | 仅 V0.1 非生产环境临时允许且强警告；生产环境禁止 |

V0.1 技术预览版如果远程 Agent 场景无法从 Portainer 后端访问 candidate 临时端口，非生产环境可以配置可达的宿主机地址，或返回向导显式选择 `startup-only` 后重新提交；系统不得运行时静默降级。`IsProduction=true` 只允许 `verified`，不得选择 `startup-only` 或 `unverified`。

失败时：

- 标记发布失败。
- 保留失败日志。
- V0.1 技术预览版自动尝试恢复旧容器，允许短暂停机；恢复失败时标记为“需人工处置”。
- V1.0 MVP 通过网关保持旧版本运行，若旧版本存在。
- 支持一键回滚。
- 分批发布时暂停后续批次。

## 24. 验收标准

### 24.1 镜像部署

- 用户可以创建项目、环境、应用、服务。
- 用户可以填写已有镜像并部署到 Docker 单机。
- 服务详情能展示运行状态、端口、日志、发布记录。
- V0.1 技术预览版允许短暂停机，但新版本启动或健康检查失败时必须自动尝试恢复旧容器。
- V0.1 技术预览版同一服务环境并发发布必须被拒绝或复用幂等结果。
- 可以重新部署；人工选择历史版本回滚在 V1.0 MVP 验收。

### 24.2 Java Jar 部署

- 用户可以上传 Java 8 Jar。
- 平台可以构建运行镜像。
- 镜像可以推送到已有 registry。
- 服务可以部署并通过健康检查。

### 24.3 前端 dist 部署

- 用户可以上传前端 dist。
- 用户可以选择 SPA 或 MPA 模式。
- 平台可以构建 Nginx 静态镜像。
- SPA 模式刷新前端路由不返回 404。
- MPA 模式按真实静态文件访问。

### 24.4 对象存储

- 用户可以配置 MinIO。
- 用户可以从 MinIO 拉取制品。
- 阿里云 OSS 兼容验证通过时可从 OSS 拉取制品；若需独立适配器，则进入 V1.0 增强验收。
- 拉取后的制品有 hash、大小和来源记录。

### 24.5 网关

- 用户可以绑定域名到服务。
- Nginx 可以自动生成并 reload 配置。
- reload 失败不会破坏旧配置。
- 网关切流失败不会影响当前线上版本。
- 可以配置 `/api` 和 `/` 分别转发到不同服务。

### 24.6 配置中心

- 用户可以维护项目级、环境级、服务级变量。
- 敏感变量默认脱敏。
- 修改配置后服务提示需要重新部署。
- 重新部署后配置生效。

### 24.7 多主机分批发布

- 一个环境可以绑定多台 Docker 主机。
- 服务可以按批次发布。
- 某一批失败后后续批次暂停。
- 发布记录可追踪每台主机结果。

### 24.8 审计

- 上传制品、构建镜像、发布、回滚、修改敏感变量、删除服务等操作均有审计记录。
- 审计记录能看到操作者、时间、对象、结果和失败原因。

## 25. 风险与约束

- 阿里云 OSS 与 S3 兼容能力需要在目标环境验证，必要时实现独立 OSS 适配器。
- 多 Docker 主机场景下，中心 Nginx 依赖业务服务发布端口可从网关节点访问。
- 不保存源码会限制 Go、Node.js、Python 等语言的源码构建能力，MVP 应鼓励使用已有镜像或镜像 tar。
- Jar 和 dist 原始制品长期保留会带来磁盘占用，需要清理能力和容量提醒。
- Nginx 配置生成必须严格校验，避免错误配置导致网关不可用。
- 敏感变量和 registry 凭据需要沿用或增强 Portainer 现有加密能力。
- V0.1 技术预览版无中心网关，固定宿主机端口替换无法承诺零停机，只承诺失败自动恢复和诊断可追踪。
- 使用可变镜像 tag 会影响回滚可复现性；发布时应解析并保存不可变 digest，无法解析时标记弱可追溯。

## 26. 已确认决策

- 首要部署目标是多台 Docker 主机，开发测试先使用 Docker 单机。
- V0.1 技术预览版只承诺 Docker 单机已有镜像部署闭环，允许短暂停机但失败必须自动恢复旧容器；V1.0 MVP 才承诺网关切流下失败不影响当前线上版本。
- 后续扩展 Kubernetes。
- 不集成 Git。
- 平台支持构建镜像，也支持部署已有镜像。
- 手动上传或 S3 拉取的制品可能是镜像、Jar、前端 dist 等。
- 私有镜像仓库只接入已有 registry，不内置。
- S3 主要目标是 MinIO；阿里云 OSS 作为兼容验证项，独立适配器不阻塞 V0.5。
- 多 Docker 主机场景接受中心 Nginx 网关加 `hostIP:publishedPort` 作为 V1.0 MVP。
- 产品模型采用 `ServiceDefinition` 和 `ServiceDeployment` 拆分，避免跨环境复制多条服务造成配置、审计和页面心智混乱。
- 平台审计新增结构化审计表，不以现有通用 `UserActivityLog` 作为 PRD 审计能力的完整实现。
- 已有镜像发布必须尽量解析并保存 digest；拿不到 digest 时允许发布但标记为弱可追溯，回滚可用性降级。
- V0.5 制品驱动版优先支持 Java 8。
- V0.5 制品驱动版支持前端 dist 的 SPA 和 MPA / 纯静态站点。
- V1.0 MVP 阶段 Python 只通过镜像部署。
- V1.0 MVP 的多主机发布先使用分批发布，不在 V1.0 内承诺复杂 HTTP 灰度。
- Gate 0A 文档与模型冻结后可启动模型、CRUD、异步框架和前端骨架；Gate 0B Docker/Agent candidate 技术 Spike 通过前，不启动 Docker 发布执行器正式编码。
- V0.1 开发前必须完成 Docker/Agent candidate 技术 Spike，覆盖容器化 Portainer + Docker socket、本地 Agent、远程 Agent、candidate 随机端口探测、版本化容器命名、candidate 验证后停止/删除、正式端口切换、旧容器恢复与私有镜像认证。
- HTTP 灰度发布作为后续增强。
- 上传或拉取的 Jar、dist、Python 包等原始制品保留，用于审计和重新构建。
- 平台提供手动清理制品能力。
