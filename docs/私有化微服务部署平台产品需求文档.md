# 私有化微服务部署平台 PRD

版本：v1.0  
日期：2026-07-09  
基础项目：Portainer Community Edition 二次开发

## 1. 背景与定位

本项目基于 Portainer Community Edition 二次开发，目标是从“容器管理面板”升级为“制品驱动的私有化微服务交付平台”。

平台不集成 Git，不在客户环境保存源码。用户以镜像、镜像 tar、Java Jar、前端 dist 包等制品作为输入，平台负责制品校验、镜像构建或导入、推送已有私有镜像仓库、部署到 Docker 主机、配置网关、记录发布历史并支持回滚。

首期目标为 Docker 单机和多台 Docker 主机，开发测试阶段优先支持 Docker 单机，后续扩展 Kubernetes。

## 2. 产品目标

### 2.1 核心目标

- 建立项目、环境、应用、服务的统一应用模型。
- 提供统一的“应用部署”入口，弱化 Stack、Container、Kubernetes YAML 等底层概念。
- 支持部署已有镜像。
- 支持从手动上传或对象存储拉取制品，并包装为运行镜像。
- 支持 Java 8 Jar、前端 dist、Docker 镜像 tar 等核心制品。
- 支持接入已有私有镜像仓库。
- 支持 MinIO 为主的对象存储，并兼容阿里云 OSS。
- 支持配置中心、敏感变量、域名、网关、证书、发布记录、回滚、日志、监控、健康检查。
- 支持管理员、项目管理员、开发者、只读观察者的权限边界。
- 支持关键操作审计。

### 2.2 非目标

MVP 阶段不做以下能力：

- Git 集成。
- 源码构建。
- 平台内置私有镜像仓库。
- 数据库实例创建、备份、恢复。
- Kubernetes 部署。
- 完整 CI/CD 流水线。
- 复杂审批流。
- 多租户计费。
- 制品漏洞扫描。
- Python 源码包构建。

## 3. 核心原则

- 私有化交付优先，不要求客户环境存在业务源码。
- 所有部署输入都必须是制品，不是源码仓库。
- 构建过程只做“制品包装”，不做源码编译。
- 最终运行物统一为镜像。
- 平台只接入已有 registry，不内置 registry。
- 日常用户从应用视角操作，底层 Portainer 能力保留在高级管理中。
- 发布失败不能影响当前线上版本。
- 敏感配置必须加密、脱敏、可审计。
- Docker 与未来 Kubernetes 部署逻辑通过适配器隔离。

## 6. 部署目标

### 6.1 Docker 单机

开发测试阶段优先支持。

能力包括：

- 在当前 Docker 环境创建容器或 Stack。
- 绑定端口。
- 配置环境变量。
- 配置卷。
- 接入中心 Nginx 网关。
- 查看容器日志和状态。

### 6.2 多 Docker 主机

MVP 支持多台 Docker 主机。

策略：

- 每个环境可以绑定一个或多个 Docker 主机。
- 服务发布时选择目标主机或主机组。
- HTTP 服务通过中心 Nginx 网关暴露。
- worker、scheduler、python-job 等非 HTTP 服务按主机分批发布。

### 6.3 Kubernetes

后续阶段支持。

映射关系：

- Project / Environment -> Namespace / Label
- Service -> Deployment / CronJob
- Config -> ConfigMap
- Secret -> Secret
- Domain Route -> Ingress
- Health Check -> Probe
- Release -> Deployment revision

## 7. 制品来源

### 7.1 已有镜像

用户直接填写镜像地址。

示例：

```text
registry.example.com/mall/order-api:1.0.0
harbor.example.com/project/admin-web:20260709
```

平台校验：

- 镜像地址格式。
- 当前 Docker 主机是否可拉取。
- registry 认证是否可用。
- 镜像元信息是否可读取。

校验通过后直接部署。

### 7.2 手动上传

用户在平台上传制品。

支持：

- `.jar`
- `.zip`
- `.tar`
- `.tar.gz`
- Docker image tar
- OCI archive

上传后平台需要：

- 限制最大文件大小。
- 计算 SHA256。
- 判断制品类型。
- 保存制品元数据。
- 保存原始制品用于审计和重新构建。
- 支持用户手动清理原始制品。

### 7.3 S3 / MinIO / 阿里云 OSS

对象存储主要目标为 MinIO，同时需要兼容阿里云 OSS。

MVP 建议实现：

- S3 兼容协议适配 MinIO。
- 阿里云 OSS 通过独立 OSS 适配器或兼容 S3 endpoint 接入，具体实现按可用 SDK 和部署环境验证。

对象存储配置项：

- 存储类型：MinIO / S3 Compatible / Aliyun OSS
- endpoint
- region
- bucket
- access key
- secret key
- path prefix
- 是否启用 TLS
- 是否跳过证书校验
- 默认下载超时
- 最大文件大小

部署时用户可以：

- 浏览对象路径，后续可选。
- 手动输入对象路径。
- 拉取制品到平台。
- 校验 SHA256，若用户提供期望 hash。
- 进入构建或导入流程。

## 8. 构建与镜像管理

### 8.1 构建定位

平台构建不是源码构建，而是制品包装。

统一流程：

1. 获取制品。
2. 校验类型、大小、hash。
3. 选择构建模板。
4. 构建运行镜像或导入镜像。
5. 打平台标准 tag。
6. 推送已有私有 registry。
7. 使用最终镜像部署。
8. 保存发布记录。

### 8.2 私有 registry

平台只接入已有 registry。

配置项：

- registry 地址
- 用户名
- 密码或 token
- 是否启用 TLS
- 是否跳过证书校验
- 默认命名空间

建议镜像 tag 规则：

```text
{registry}/{project}/{environment}/{application}-{service}:{version}
```

示例：

```text
registry.local/mall/prod/order-api:20260709-153012
```

### 8.3 Java Jar 构建

MVP 优先支持 Java 8。

用户配置：

- Java 版本：默认 Java 8
- Jar 文件
- 启动参数
- JVM 参数
- 服务端口
- 健康检查路径
- 工作目录
- 环境变量

平台行为：

- 使用受控 Java 8 基础镜像。
- 将 Jar 包复制到固定工作目录。
- 生成标准启动命令。
- 构建镜像并推送 registry。
- 部署生成镜像。

### 8.4 前端 dist 构建

支持上传或从对象存储拉取前端 dist 压缩包。

前端 dist 运行模式：

- SPA：单页应用，刷新任意前端路由回退到 `index.html`。
- MPA / 纯静态站点：多页面或普通静态站点，路径按真实文件解析，不做统一 fallback。
- 静态资源包：只作为资源目录被其他服务引用，MVP 不作为独立部署类型优先实现。
- SSR / Node 前端服务：不按 dist 构建处理，MVP 要求用户提供已有镜像。

MVP 支持：

- SPA
- MPA / 纯静态站点

用户配置：

- 运行模式：SPA / MPA
- 默认首页
- 服务端口
- 是否启用 gzip
- 静态资源缓存策略
- 404 页面，后续可选

平台行为：

- 解压 dist。
- 校验入口文件。
- 使用受控 Nginx 静态镜像。
- 生成站点 Nginx 配置。
- 构建镜像并推送 registry。
- 部署生成镜像。

### 8.5 镜像 tar 导入

支持 Docker image tar 和 OCI archive。

平台行为：

1. 导入镜像。
2. 读取镜像元信息。
3. 展示原始镜像名称、tag、架构、创建时间。
4. 重新打平台标准 tag。
5. 推送已有 registry。
6. 部署标准 tag。

### 8.6 Python 服务

MVP 阶段 Python 仅支持已有镜像部署。

适用场景：

- FastAPI Web 服务。
- 定时任务。
- 脚本任务。

用户需要自行准备镜像并推送到 registry，或上传镜像 tar 后由平台导入。

后续可扩展：

- pex
- pyz
- wheel
- 混淆后的 Python 包

## 9. 应用部署入口

### 9.1 入口目标

用户不需要直接从 Stack、Container 或 YAML 开始。

部署入口以应用视角组织：

1. 选择项目。
2. 选择环境。
3. 选择应用。
4. 选择或创建服务。
5. 选择服务类型。
6. 选择制品来源。
7. 配置端口、域名、环境变量、数据库连接。
8. 执行校验。
9. 一键部署。

### 9.2 服务类型

MVP 支持：

- Java 后端
- 前端静态站点
- 已有镜像服务
- Worker
- Scheduler
- Python 镜像服务
- Python 镜像任务

后续支持：

- Go 后端模板
- Node.js 后端模板
- 更多语言运行模板

由于不集成 Git 且不保存源码，Go、Node.js 等服务在 MVP 中建议优先通过已有镜像或镜像 tar 部署。

### 9.3 部署前校验

部署前必须校验：

- 项目、环境、应用、服务是否完整。
- 制品是否可用。
- 制品 hash 是否一致。
- registry 是否可推送。
- Docker 主机是否在线。
- 镜像是否可拉取。
- 端口是否冲突。
- 域名路由是否冲突。
- 健康检查配置是否合理。
- 敏感变量是否完整。
- 数据库连接是否可用，若服务依赖数据库。

## 10. 配置中心

### 10.1 配置层级

支持三级配置：

- 项目级配置
- 环境级配置
- 服务级配置

优先级：

```text
服务级 > 环境级 > 项目级
```

### 10.2 配置类型

- 普通环境变量
- 敏感环境变量
- 引用变量
- 数据库连接变量
- Redis 连接变量

### 10.3 敏感变量

要求：

- 加密保存。
- 页面默认脱敏。
- 复制和查看明文需要权限。
- 修改后记录审计。
- 发布时注入容器环境变量。
- 不在日志和审计详情中明文展示。

### 10.4 配置变更提示

服务运行后，如果配置发生变化，应提示：

```text
配置已变更，当前运行实例尚未重新部署。
```

用户可以：

- 查看配置差异。
- 立即重新部署。
- 稍后处理。

## 11. 数据库连接

MVP 只做数据库连接管理和工作台，不创建数据库实例。

能力包括：

- 管理数据库连接。
- 测试连接。
- 应用绑定数据库连接。
- 生成环境变量。
- 打开数据库工作台。
- 执行 SQL 操作并记录审计。

可生成变量：

```text
DATABASE_HOST
DATABASE_PORT
DATABASE_USER
DATABASE_PASSWORD
DATABASE_NAME
DATABASE_URL
```

## 12. 网关、域名与证书

### 12.1 内置 Nginx 的目的

内置 Nginx 的目标是提供统一入口，而不是替代业务服务。

它解决：

- 统一域名访问入口。
- 自动反向代理到 Docker 服务。
- HTTPS 证书挂载和切换。
- 路径转发，例如 `/api` 到后端，`/` 到前端。
- 避免用户直接暴露大量容器端口。
- 为灰度或分批发布提供流量控制基础。
- 多 Docker 主机场景中提供中心入口。

### 12.2 Docker 单机场景

平台部署一个受控 Nginx 容器。

发布 HTTP 服务后：

- 自动生成 upstream。
- 自动生成 server 和 location。
- 校验 Nginx 配置。
- reload Nginx。
- reload 失败则保持旧配置。

### 12.3 多 Docker 主机场景

MVP 接受中心 Nginx 网关模式。

模式：

- 指定一台 Docker 主机作为网关节点。
- Nginx 部署在网关节点。
- 业务服务部署在一台或多台 Docker 主机。
- Nginx 通过 `hostIP:publishedPort` 转发到业务服务。

后续可扩展：

- 每台主机边缘 Nginx。
- Keepalived 高可用入口。
- Kubernetes Ingress。

### 12.4 域名与路由

每个 HTTP 服务支持：

- 域名。
- 路径前缀。
- 目标端口。
- HTTPS 开关。
- 强制 HTTPS。
- WebSocket 支持。
- 代理超时。
- 最大上传大小。

示例：

```text
admin.example.com/      -> frontend:80
api.example.com/        -> backend:8080
example.com/api         -> backend:8080
example.com/            -> frontend:80
```

### 12.5 证书管理

MVP 支持：

- 手动上传证书。
- 选择已有证书。
- 服务绑定证书。

后续支持：

- ACME 自动签发。
- 证书过期提醒。

## 13. 发布管理

### 13.1 发布状态

发布状态包括：

- 待校验
- 校验中
- 构建中
- 推送中
- 部署中
- 健康检查中
- 成功
- 失败
- 已回滚
- 已取消

### 13.2 标准发布流程

1. 选择项目、环境、应用、服务。
2. 选择制品来源。
3. 填写版本号。
4. 配置端口、环境变量、域名、健康检查。
5. 执行部署前校验。
6. 构建或导入镜像。
7. 推送 registry。
8. 在目标 Docker 主机部署。
9. 更新 Nginx 网关。
10. 执行健康检查。
11. 保存发布记录。

### 13.3 重新部署

使用当前版本重新部署。

适用场景：

- 配置已变更。
- 容器异常。
- 主机迁移。
- 手动恢复。

### 13.4 回滚

用户选择历史发布版本回滚。

流程：

1. 校验历史镜像是否仍存在。
2. 展示版本差异和配置差异。
3. 用户二次确认。
4. 部署历史镜像。
5. 更新网关。
6. 执行健康检查。
7. 记录回滚发布。

### 13.5 分批发布

MVP 优先支持分批发布。

适用：

- HTTP 服务。
- worker。
- scheduler。
- python-job。

配置项：

- 每批主机数量。
- 每批间隔。
- 失败是否暂停。
- 健康检查失败是否回滚。

### 13.6 灰度发布

第一阶段可以暂缓复杂灰度，先全部使用分批发布。

后续 HTTP 服务支持基于 Nginx upstream 权重的灰度发布：

```text
v1: 90%
v2: 10%
```

能力包括：

- 创建灰度版本。
- 设置流量比例。
- 扩大比例。
- 全量切换。
- 取消灰度。
- 灰度失败回滚。

非 HTTP 服务不做流量灰度，只做分批发布。

平台提供手动清理能力：

- 按项目清理。
- 按服务清理。
- 按时间清理。

## 24. 验收标准

### 24.1 镜像部署

- 用户可以创建项目、环境、应用、服务。
- 用户可以填写已有镜像并部署到 Docker 单机。
- 服务详情能展示运行状态、端口、日志、发布记录。
- 可以重新部署和回滚。

### 24.2 Java Jar 部署

- 用户可以上传 Java 8 Jar。
- 平台可以构建运行镜像。
- 镜像可以推送到已有 registry。
- 服务可以部署并通过健康检查。

### 24.3 前端 dist 部署

- 用户可以上传前端 dist。
- 用户可以选择 SPA 或 MPA 模式。
- 平台可以构建 Nginx 静态镜像。
- SPA 模式刷新前端路由不返回 404。
- MPA 模式按真实静态文件访问。

### 24.4 对象存储

- 用户可以配置 MinIO。
- 用户可以从 MinIO 拉取制品。
- 用户可以从阿里云 OSS 拉取制品，具体方式按最终适配器实现验收。
- 拉取后的制品有 hash、大小和来源记录。

### 24.5 网关

- 用户可以绑定域名到服务。
- Nginx 可以自动生成并 reload 配置。
- reload 失败不会破坏旧配置。
- 可以配置 `/api` 和 `/` 分别转发到不同服务。

### 24.6 配置中心

- 用户可以维护项目级、环境级、服务级变量。
- 敏感变量默认脱敏。
- 修改配置后服务提示需要重新部署。
- 重新部署后配置生效。

### 24.7 多主机分批发布

- 一个环境可以绑定多台 Docker 主机。
- 服务可以按批次发布。
- 某一批失败后后续批次暂停。
- 发布记录可追踪每台主机结果。

### 24.8 审计

- 上传制品、构建镜像、发布、回滚、修改敏感变量、删除服务等操作均有审计记录。
- 审计记录能看到操作者、时间、对象、结果和失败原因。

## 25. 风险与约束

- 阿里云 OSS 与 S3 兼容能力需要在目标环境验证，必要时实现独立 OSS 适配器。
- 多 Docker 主机场景下，中心 Nginx 依赖业务服务发布端口可从网关节点访问。
- 不保存源码会限制 Go、Node.js、Python 等语言的源码构建能力，MVP 应鼓励使用已有镜像或镜像 tar。
- Jar 和 dist 原始制品长期保留会带来磁盘占用，需要清理能力和容量提醒。
- Nginx 配置生成必须严格校验，避免错误配置导致网关不可用。
- 敏感变量和 registry 凭据需要沿用或增强 Portainer 现有加密能力。

## 26. 已确认决策

- 首要部署目标是多台 Docker 主机，开发测试先使用 Docker 单机。
- 后续扩展 Kubernetes。
- 不集成 Git。
- 平台支持构建镜像，也支持部署已有镜像。
- 手动上传或 S3 拉取的制品可能是镜像、Jar、前端 dist 等。
- 私有镜像仓库只接入已有 registry，不内置。
- S3 主要目标是 MinIO，同时兼容阿里云 OSS。
- 多 Docker 主机场景接受中心 Nginx 网关加 `hostIP:publishedPort` 作为 MVP。
- Java 优先支持 Java 8。
- 前端 dist MVP 支持 SPA 和 MPA / 纯静态站点。
- Python MVP 只通过镜像部署。
- 第一阶段可以先全部使用分批发布。
- HTTP 灰度发布作为后续增强。
- 上传或拉取的 Jar、dist、Python 包等原始制品保留，用于审计和重新构建。
- 平台提供手动清理制品能力。
